# Remote Control parity: `sm` vs Claude Code Remote Control

Goal (PLAN-v2-ade.md §4.10): work starts on your computer, keeps running there, and you pick it
up on your phone in one step. The same experience as Claude Code Remote Control, for any ACP
agent.

This is a feature-by-feature table. The left column is Claude Code Remote Control as we
understand it (from the product documentation as of this writing; nothing here was checked
online, so treat the left column as a checklist to confirm during M2B-020, not as a quotation).
The right columns are this repository.

**Status values**

- **done**: built and covered by an automated test; the evidence column names it.
- **done (e2e)**: also exercised end to end by `cargo run -p cli -- e2e rc` (headless client-core
  as the phone) and `web/tests/rc.spec.js` (the mobile web page as the phone).
- **partial**: works, with a named gap.
- **planned**: not built; the milestone that builds it.
- **differs**: deliberately not the same; the reason.
- **real device**: only a person with a laptop and a phone can confirm it (M2B-020).

## How to use this table for M2B-020

Install `sm` on a laptop, `sm login`, then walk the sections in order. Every row marked **real
device** is a thing to try; write down anything that does not match the right column. The
automated checks use a local hub (`wrangler dev`), an acp-mock agent and a headless phone, so
they say nothing about a real harness login, a real sleep or a real phone browser.

## Gaps found while building the check (M2B-019)

1. **A terminal line typed during a running task is dropped.** `sidecar::bridge` allows one
   running task per thread. The phone's prompts are queued by the hub (`pending` tasks), but a
   prompt typed in the TUI goes straight to the bridge, which refuses it
   (`thread ... already has a running task`), and the TUI shows nothing: no message in the log,
   no notice. Remote Control lets both sides type at any time. The check types again after the
   turn, and asserts the invariants that matter (one answer applied once, gap-free transcript).
2. **Presence and snapshot events are in the transcript.** `Presence` and `StateSnapshot` take
   `seq` numbers, so a client that counts "messages" by `seq` must not. The checks count by type.
3. **No "new session" on the mobile web page.** A session can be started from the phone only by
   a client that calls `POST /v1/threads`.
