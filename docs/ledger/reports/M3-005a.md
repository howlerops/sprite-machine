# M3-005a report: composer wired into the open thread

## Summary
- `AppShell` owns one `ThreadComposer` and draws it under the open thread's transcript (`render_thread`: transcript pane above, composer below, plan/usage column on the right). `AppShell::thread_composer()` exposes it.
- Every `ThreadSnapshot` calls `composer.set_thread(&view)`; switching threads clears the composer's thread at once and its prompt text on the next render.
- `ComposerEvent`s go through the link's outbox (`SessionLink::enqueue`, flushed on the link thread):
  - `Send` -> `Intent::Prompt` with fresh `tk_`/`msg_` ids and one text part.
  - `Cancel(intent)` and `Intent(intent)` (SetSession, RemovePending) -> enqueued as they are (each gets its `idk_` Idempotency-Key in the outbox).
- 409 `task_started` on a removal: `ThreadSnapshot.started_removals` (task ids of this thread from `Outbox::started_removals()`) -> `ThreadComposer::set_started_removals`. The composer then shows the message "That message already started, so it could not be removed. Stop it instead." (`thread-started-notice`) and the Stop button, which cancels that task (unless the thread's events already show it finished). Clicking Stop dismisses the conflict entries for that task from the outbox, then enqueues the cancel.
- Runner cap: `set_runner_mode` is fed from the hosting machine's `capabilities.features` (`permission_mode:<mode>`). The shell looks the thread's `machine_id` up in the machines list the new-task composer already fetches (`GET /v1/machines`). `parse_machines` now reads `features` through `cap_from_features` first and falls back to the plain `permission_mode` field. It is re-derived when the machines list arrives (observer on the new-task composer) and on every snapshot.
- New-task composer unchanged: Cmd/Ctrl+N still focuses its prompt (palette tests pass).

## Discovered work
```yaml
- title: shell has no machine-capabilities source of its own; the runner cap reuses the new-task composer's machines list
  detail: >
    The cap for the open thread is looked up in ComposeView's machines list (GET /v1/machines, loaded when
    the shell has a session). If that fetch fails or the machine is not listed, the cap stays unset and every
    session mode is offered. A shell-level machines feed (refreshed on presence changes) would remove the coupling.
  paths: [crates/client-gpui/src/shell/**, crates/client-gpui/src/compose/**]
- title: Send before the first snapshot of a thread is dropped silently
  detail: >
    ThreadComposer::send_text returns when no thread is set. The Send button is visible before the snapshot
    arrives; disable it (or keep the text) until set_thread has run.
  paths: [crates/client-gpui/src/compose/thread.rs]
- title: a started-removal conflict stays in the outbox until the user presses Stop
  detail: >
    started_removals entries are dismissed on Stop. If the task finishes first, the entry lingers (harmless: the
    composer ignores tasks the view shows finished) but is never pruned. Prune finished tasks' conflicts in the link.
  paths: [crates/client-gpui/src/shell/link.rs]
- title: flaky test the_banner_follows_a_client_core_connection (also pairing_shows_a_qr... under load)
  detail: >
    "Detected activity on thread session-link ... test is not deterministic" about 1 in 30 runs, on v2 too. The
    test opens a signed-in shell whose link thread wakes gpui tasks without allow_parking / a deterministic hand-off.
  paths: [crates/client-gpui/tests/shell.rs]
- title: DELETE pending role mismatch (from M3-005b) still open; a member's chip removal will 403 and show nothing
  detail: The composer does not surface Rejected outbox entries for SetSession / RemovePending.
  paths: [crates/client-gpui/src/shell/view.rs, docs/specs/client-api.md]
```
