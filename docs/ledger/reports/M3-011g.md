# M3-011g: approval card shows why an answer was refused

## Summary

- A click that the controller refuses locally now stays on that card. `ApprovalController::answer` records the refusal for `Expired`, `NotOpen` and `Outbox` (a queue write failure), and the card shows it as a `Failed` status line, reusing the existing `approval-failed` display ("Your answer was not delivered: ...").
- The card's buttons follow the real state of the request, not the displayed status. So a queue failure on an open request keeps the buttons working, and the next answer that goes through clears the message. An expired or already-answered request stays unanswerable, as before.
- The refusal is shown through the existing snapshot path: the link runs the answer on its thread, then publishes a snapshot. The shell's `on_card_action` still drops the `Receiver`; nothing was lost, because the refusal is in the snapshot the card is built from.
- The message clears when the next answer succeeds, or when the thread's cards close (`AppShell::close_thread` calls `SessionLink::forget_refusals`). Switching to another thread starts a new controller, so its refusals go too.
- `AnswerError::UnknownInterrupt`, `UnknownOption` and `AlreadyAnswering` are not shown (see discovered work). The card cannot produce them: its buttons come from the card's own options and are disabled while an answer is on its way.

## Files

- `crates/client-gpui/src/approval/controller.rs`: `answer` wraps the old body (now `queue_answer`); it records or clears the card's refusal. New `refused` map, `refusal_text`, `clear_refusals`.
- `crates/client-gpui/src/approval/model.rs`: `CardContext` gains `refused` (no longer `Copy`); `build_card` computes `answerable` from the real state and shows the refusal as `CardState::Failed`; `ApprovalCard` gains `answerable`, and `is_answerable` returns it.
- `crates/client-gpui/src/approval/view.rs`: the preset checkbox uses `card.is_answerable()` instead of comparing the displayed state.
- `crates/client-gpui/src/shell/link.rs`: `forget_refusals`.
- `crates/client-gpui/src/shell/view.rs`: `close_thread` calls `forget_refusals`.
- `crates/client-gpui/locales/en/approval.ftl`: `approval-refused-expired`, `approval-refused-not-open`, `approval-refused-outbox`.
- `crates/client-gpui/tests/approval.rs`: four tests (one per refusal kind, plus the clear-on-close test).
- `crates/client-gpui/tests/shell.rs`: `a_click_refused_as_expired_says_so_on_the_card` (click through the real window and link).

## Criteria

1. **A locally refused click shows a Fluent message on that card.** Met. `a_click_refused_as_expired_shows_why_on_the_card` asserts `CardState::Failed { message: "the request expired before your answer was sent" }`. The message comes from `approval-refused-expired` in `approval.ftl`, via `tr` in `controller.rs`. The shell test checks the rendered `approval-status` text: "Your answer was not delivered: the request expired before your answer was sent".
2. **One test per error kind.** Met.
   - Expired: `a_click_refused_as_expired_shows_why_on_the_card` (controller) and `a_click_refused_as_expired_says_so_on_the_card` (shell, through the window).
   - NotOpen: `a_click_refused_as_not_open_shows_that_it_was_already_answered`.
   - Outbox: `an_answer_the_outbox_cannot_queue_is_shown_and_the_next_answer_clears_it`. The failing write is produced by removing the cache's directory after it is opened, so SQLite cannot create its journal. The test checks that the card stays answerable.
3. **The message clears on the next successful action or when the card closes.** Met.
   - Next successful action: the Outbox test answers again and the card goes to `Sending` (not `Failed`).
   - Card closes: `a_refusal_clears_when_the_card_closes` (controller). `AppShell::close_thread` calls `forget_refusals`, and this path has no separate shell-level test.
4. **Each test fails without the change.** Met, as shown in the Verify section.
5. **The strings catalog test stays green.** Met. `every_string_is_in_the_catalog_and_every_catalog_string_is_used` passes; the three new ids are used through `tr` in `controller.rs`.

  lane: client
  files: [crates/client-gpui/src/approval/controller.rs]
- id: M3-011g-D3
  title: "shell: the card-action path drops the answer's receiver"
  why: "AppShell::on_card_action still drops SessionLink::answer's Receiver. The refusal reaches the card through the snapshot, so nothing is lost today, but a caller that needs the result (a toast, a retry) would have to read the receiver. Consider reading it into a status or removing the receiver."
  lane: client

If the journal mode changes, or the test runs on another OS (where the open file cannot be removed), it should use a different failure injection."
  lane: infra
  files: [crates/client-gpui/tests/approval.rs]
