# M3-011k: approval card: an HTTP-failed answer on a still-open request stays answerable

## Summary

- After the hub refuses an answer over HTTP (any 4xx except 409 and 410) or transient failures use up the retry budget, the card's option buttons stay enabled while the request is still open. Clicking one sends a new answer with a new `Idempotency-Key` (the outbox's `enqueue` makes a fresh key per answer).
- `build_card` now decides `answerable` from the request's real state, not from `CardState`. `Open` is answerable. `Failed` is answerable only when the controller marked the answer retryable, the interrupt is still open (no resolution, no 409 winner) and not expired by the clock. Every other state is not answerable.
- A 409 stays unanswerable, both with a winner (`AlreadyResolved`) and without one (`Failed` "conflict unknown", which the controller never marks retryable). A 410 stays unanswerable: the hub has expired the request.
- The controller tracks retryability per interrupt in `sync`, from the outbox state: `Rejected` (not 410) and `Exhausted` set it; every other state clears it. A new successful answer clears it too.

## Files

- `crates/client-gpui/src/approval/controller.rs`: new `retryable` set, maintained in `sync` and cleared in `queue_answer`; `CardContext` is built with `retryable`.
- `crates/client-gpui/src/approval/model.rs`: `CardContext` gains `retryable: bool`; `build_card` computes `answerable` from the underlying state, the retry flag, `view.is_open()` and expiry.
- `crates/client-gpui/tests/approval.rs`: the old controller-only retry test (410) is replaced by four state tests and one widget test:
  - `a_refused_answer_on_an_open_request_leaves_the_card_answerable_and_a_retry_gets_a_new_key` (400, controller)
  - `a_transient_failure_that_runs_out_of_retries_leaves_the_card_answerable` (503, retries exhausted)
  - `an_expired_refusal_shows_the_failure_and_leaves_the_card_unanswerable` (410)
  - `a_409_without_a_winner_keeps_the_card_unanswerable`
  - `a_refused_answer_is_sent_again_from_the_card_buttons_with_a_new_key` (widget: renders the transcript pane, clicks `approval-option-allow`, flushes a 400 from the hub, re-renders, clicks `approval-option-reject` through the card widgets, asserts two outbox entries with different keys)

`client-core` and the shell were not touched.

## Criteria

1. **After a refused HTTP answer on an open request the option buttons are enabled.** Met. `a_refused_answer_on_an_open_request_...` asserts `is_answerable()` and every option `enabled`, after a 400 with the status line "bad_outcome (HTTP 400)". The widget test confirms it through the rendered buttons.
2. **Clicking one through the card widgets sends a new answer with a new Idempotency-Key.** Met. `a_refused_answer_is_sent_again_from_the_card_buttons_with_a_new_key` clicks `approval-option-reject` in a window, and the outbox then holds two entries with different keys and the `reject` body. It fails without the change.
3. **After a 409 the buttons stay disabled.** Met. `a_409_shows_already_resolved_by_the_winner` (existing) and `a_409_without_a_winner_keeps_the_card_unanswerable` (new) assert every option disabled.
4. **Tests fail without the change.** Met, as in Verify.
5. **Existing behaviour kept.** Met. The M3-011g local refusals still show their messages and keep the buttons working (the outbox-failure test passes). The 410 retry behaviour changes on purpose: see the judgment call below.

## Judgment calls

- **410 stays unanswerable.** The old test retried after a 410 at controller level. The hub has said the request is over, and the card already disables buttons for an expired request, so the card now stays disabled. The controller itself still accepts a call to `answer` (it does not gate on the card), so this is a UI rule, not a hard block.
- **Other 4xx count as "still open".** The card cannot know whether a 400, 403 or 404 is permanent. Those buttons come back, and a repeat refusal shows the same failure again. Narrowing this needs the hub to say whether the request is still open.
