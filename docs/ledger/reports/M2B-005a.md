# M2B-005a: device pairing security

## Summary

- Tunnel: `GET /v1/machines/{id}/tunnel` now asks `devices::trust::tunnel_verdict` (the `machine_may_connect` rule, split so a revoked machine still gets the DO's `auth_revoked` close). A machine not vouched for while the org has `require_trusted_devices` on is refused with HTTP 401 before the upgrade (tunnel.md §2: the status of a missing credential; there is no socket yet to close with a code).
- Rate limits (D1 table `device_attempts`, sliding windows, injected clock): failed user-code attempts 5/min and 20/hour per user and per org on approve (and deny, same oracle) -> `429` + `Retry-After`; `POST /v1/devices/code` 10/min per `CF-Connecting-IP` and at most 1000 live pairings. Expired pairings (1 h grace, so a late poll still gets `expired_token`) and old counters are purged by an hourly Cron Trigger and on every start.
- Token response now has `org {id,name}` and `approved_by {id,name,email}`. `sm login` prints them, asks "Join org X approved by Y? [y/N]" (`--yes` skips; no TTY without `--yes` = no), and on "no" stores nothing and calls new `DELETE /v1/devices/self` with the new machine credential, which revokes it.

Design notes:
- `ApiError` (threads/error.rs) is outside scope and has no header field, so a 429 is `ApiError{429, rate_limited, "too many attempts; retry in N seconds"}` and `limits::retry_after(&ApiError)` (tested) gives the route its `Retry-After`.
- A machine with no `machines` row (only the DEV_FIXTURES credential route makes those) is `Untrusted`, except under DEV_FIXTURES, where the dev org's setting decides. This is what lets the live test have an unvouched machine (`machines.origin` has a CHECK limited to admin/device, so no D1 row can be unvouched), and keeps `machine_do` passing.
- Runner display strings from the hub (org and user names) have control characters stripped before printing.
- Deny shares the approve limit (it is the same user-code oracle); not literally asked for.

## Acceptance criteria

1. MET. Tunnel refuses untrusted with 401. Live `the_tunnel_refuses_a_machine_that_is_not_vouched_for_when_the_org_requires_trusted_devices` (unvouched dev-credential machine connects with the setting off, gets `HTTP/1.1 401` with it on; an admin-issued machine and a freshly paired device machine still open a tunnel and get `welcome`; connects again when off). Native `devices::tests::the_tunnel_verdict_follows_origin_revocation_and_the_org_setting` (admin/device allowed, unknown origin refused, revoked -> forwarded for `auth_revoked`, no row). Existing `the_trusted_devices_setting_is_admin_only_and_keeps_admin_machines_allowed` still passes through the gate. Would fail without the change: the unvouched machine would get 101.
2. MET. Native: `failed_approvals_are_limited_per_minute_and_come_back_after_the_window`, `failed_approvals_are_limited_per_hour`, `the_org_limit_spans_users_and_a_success_resets_nobody`, `deny_shares_the_guessing_limit`, `starting_is_limited_per_ip_and_by_the_number_of_live_pairings`, `purge_removes_long_expired_pairings_and_old_counters_and_start_does_it_too`, `retry_after_reads_only_rate_limit_errors`. Live: `guessing_user_codes_is_limited_per_user_and_org_with_retry_after` (5x 404, then 429 + `Retry-After` 1..60, another user of the org also 429, and approve works again after the window). The scheduled purge is `worker.rs` `#[event(scheduled)]` -> `devices::routes::purge_scheduled` -> `limits::purge`, cron `17 * * * *`; the purge logic itself is tested natively, the cron wiring only compiles (not exercised live).
3. MET. Hub native `the_token_names_the_approving_org_and_user`, `a_machine_revokes_itself_with_its_own_credential_only`; live `the_token_names_the_org_and_approver_and_a_machine_can_revoke_itself` (token has org name/id and approver name; `DELETE /v1/devices/self`: session token and no auth -> 401, machine credential -> 200, device shows `revoked_at`, repeat -> 401). Runner `accepting_shows_the_org_and_approver_and_stores_the_credential` (stores), `declining_stores_nothing_and_the_hub_sees_the_revoke` (nothing stored, fake hub saw `DELETE /v1/devices/self` with `Bearer <credential>`), `no_terminal_and_no_yes_means_no`, `a_failed_revoke_still_stores_nothing_and_says_who_to_ask`, `yes_skips_the_question_and_hostile_names_cannot_move_the_cursor`, `sm_login_without_yes_and_without_a_terminal_does_not_store` (real binary), and the existing end-to-end test now passes `--yes`.
