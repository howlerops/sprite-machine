# M2B-006: runner: local harness discovery + local logins/MCP passthrough

## Summary

- `runner::harness` finds claude, codex, opencode, pi, gemini and goose (each through its ACP entry point) on PATH, then in `~/.local/bin`, and reports command + args per harness.
- The invocations live in one table (`HARNESSES`). They are unconfirmed against upstream: this worktree was built offline, so each row needs a real `session/new` to confirm.
- `capabilities()` builds the hello `Capabilities` (tunnel.md §3.1) in stable table order. `spawn_command()` inherits the runner environment unchanged.
- `local_mcp_servers()` converts `.mcp.json` and `~/.claude.json` entries (stdio and http only) into ACP `McpServer` values. Env values and headers pass through and are never logged.
- 15 integration tests in `crates/runner/tests/discovery.rs`; all verify commands pass.

## Acceptance criteria

1. **Met.** `harness::discover(path_env, home)` detects all six harnesses and their adapters, checks the execute bit, follows symlinks, takes the first match and ignores dangling links.
   - `finds_all_six_harnesses_with_their_acp_invocation`
   - `cli_without_its_acp_adapter_is_not_a_harness` (`claude` and `codex` CLIs alone are not harnesses)
   - `first_path_directory_wins`, `preferred_adapter_name_wins_within_a_harness`
   - `non_executable_file_is_ignored`
   - `symlink_is_followed_and_dangling_symlink_is_ignored`
   - `none_found_when_path_is_empty`
   - `per_user_bin_dir_is_searched_after_path` (the extra `home` fallback, see below)
2. **Met, with two notes.** `harness::capabilities(&found, max_sessions)` gives harness names in table order, `spawn: ["same_dir","worktree"]` and `host_mode: "local"`.
   - `capabilities_match_the_hello_in_tunnel_spec`: serialized JSON equals the spec example with `features: []`.
   - `harness_names_are_in_table_order_whatever_order_discovery_gave`
   - Notes: the hello example is in tunnel.md §3.1, not §3.2 as the item says. `features` is empty because the spec example advertises features the runner does not yet ship.
3. **Met.** `harness::spawn_command` does not clear or copy env; the child inherits it.
   - `spawn_inherits_the_environment_and_passes_the_acp_args`: a stub harness prints the key, `HOME`, `PATH` and cwd, and the test checks them. The key is set on the test process (fake value) and asserted absent from the command's explicit env (`get_envs`).
4. **Met, with the source notes below.** `harness::local_mcp_servers(home, project_dir)` returns sorted `McpServer` values.
   - `local_mcp_servers_merge_claude_sources_in_precedence_order`: precedence, sse and malformed entries skipped, env and headers passed through.
   - `user_level_servers_come_through_when_the_project_has_none`
   - `missing_config_files_mean_no_servers`
   - `malformed_config_is_an_error_that_does_not_show_its_values`
   - Sources, in precedence order (first name wins): `~/.claude.json` `projects[<project>].mcpServers` (local scope, which I added beyond `.mcp.json` and the top-level `mcpServers`), `<project>/.mcp.json`, and `~/.claude.json` top-level `mcpServers`.

## Decisions and deviations

- **`home` fallback**: `discover` also searches `home/.local/bin` after PATH, where the Claude installer puts its binaries. The item says "on PATH" only. This is a deliberate addition; it is easy to remove.
- **Invocations are data, not verified.** Table rows follow PLAN §4.10 and line 388. The gemini flag `--experimental-acp` and the pi adapter names are the least certain.
- **MCP `command` is passed verbatim.** The ACP schema says "absolute path". Bare names such as `npx` are not resolved against PATH. Left as discovered work.
