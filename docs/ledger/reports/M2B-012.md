# M2B-012: Attachments end to end (attempt 2)

## Summary

- `cli e2e attachments` passes against the real hub on `wrangler dev --local`: a PNG and a text file go through `POST /v1/attachments` + PUT, then one prompt on a thread hosted on an in-process `sm rc` server. The agent gets an `image` block with the PNG and an `@.sm/attachments/notes.txt` reference; the workspace file has the uploaded sha256.
- A cross-org URL, a tampered URL and an oversize file each end their task with `RunError{code:"attachment"}`; the agent never gets those prompts and `.sm/attachments/` holds only `notes.txt`.
- The bridge takes its attachment policy from `Config.file_policy` (default: production). The loopback policy is built only by `FilePolicy::loopback_for_tests`, which exists only under the `test-support` feature (enabled by cli's `runner` dependency). `sm` has no flag or env var for it.
- Attempt 1 was blocked on the bridge hardcoding `FilePolicy::default()`; the leader approved the sidecar change.

## The loopback guard, and its limits

- Compile-time: `loopback_for_tests` and `run_with_file_policy` do not exist without `test-support`. `cargo tree -p runner -e features` shows no `test-support` for the runner package on its own, so the `sm` binary built from that package has neither.
- Only the cli depends on the feature. The cli's `e2e attachments` is the one caller of `run_with_file_policy`.
- Limit 1: under a workspace-wide build, cargo unifies features, so `sm` built in the same invocation as the cli has the constructor compiled in. Nothing in `sm` calls it, and no flag or env var selects it.
- Limit 2: `FilePolicy.insecure_loopback_for_tests` is still a `pub` field, because the existing sidecar integration tests set it directly. Product code could write the struct literal. The constructor and `run_with_file_policy` are the sanctioned path; removing the literal path would mean changing those tests too.

## Acceptance criteria

1. **Met.** `cli e2e attachments`, check 1 (`crates/cli/src/e2e/attachments.rs`, `checks`). The agent's recorded `session/prompt` has `{type:"image", mimeType:"image/png", data: base64(PNG)}` and `{type:"text", text:"@.sm/attachments/notes.txt"}`. The file on disk has the uploaded sha256 (`df03d644…8d54`).
2. **Met.** `cli e2e attachments`, check 2. Each case ends with `RunError{code:"attachment"}`:
   - Cross-org: the org segment of the URL is rewritten. The signature covers the org, so the hub answers 403 (`tk_e2e_cross_org`). Only the dev org exists, so this stands in for a URL signed for another org.
   - Tampered: the last signature character is flipped; 403 (`tk_e2e_tampered`).
   - Oversize: 2048 bytes against a 1 KiB cap, refused before any fetch (`tk_e2e_oversize`).
   - The agent received one prompt in total, and `.sm/attachments/` holds only `notes.txt`.
3. **Met.** `runner::server::file_policy_tests::the_production_policy_refuses_loopback` and `runner::server::file_policy_tests::the_loopback_policy_comes_only_from_the_test_constructor` (under `test-support`). Compile-time gate as described above; `sm` has no flag or env var (`crates/cli/src/main.rs` and `RcArgs::parse` unchanged).

## Notes

- The shared target dir is rebuilt by other worktrees. During a run, `target/debug/cli` can be replaced, so the check copies its own binary (`/proc/self/exe`, falling back to `current_exe`) into its work dir and the stub runs that copy. Without this, the agent started from another build and the first run failed.
- The wrangler run needs `--var ATTACHMENT_SIGNING_KEY:<random 32 bytes hex>`; the tracer does not pass it, so the tracer is unchanged.
