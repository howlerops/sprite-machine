# M2-011 report: hub notifications via Queues (Web Push)

## Summary

- Thread DO appends of Interrupt, RunFinished{success|interrupt} and RunError enqueue an ids-only job on NOTIFY. The queue consumer applies prefs (class, per-thread mute, quiet hours with time zone), collapses per task (Topic = task id), sends RFC 8291 + RFC 8292 Web Push, deletes subscriptions on 404/410 and retries 5xx/429 through the queue.
- Routes: `POST/DELETE /v1/push/subscriptions`, `GET/PUT /v1/push/prefs`, plus `GET /v1/push/vapid-public-key`. APNs and FCM are stubs behind `PushProvider` that answer `NotConfigured`.
- Approvals are actionable: the payload carries `interrupt_id` and allow/deny actions with the option ids; the phone answers through the existing `POST /v1/threads/{id}/interrupts/{id}` (documented in `notify/mod.rs`).

## Acceptance criteria

1. Met. Routes and member gate, idempotent per endpoint (201 then 200, same id): native `subscribe_is_idempotent_per_endpoint_and_belongs_to_user_and_device`, `subscribe_needs_member_and_valid_input`, `unsubscribe_removes_only_the_callers_subscription`, `prefs_default_then_round_trip_through_d1`; live `the_push_routes_validate_and_authenticate` (includes `Europe/Berlin` resolving on the Worker and `Mars/Base` giving 400). The subscription row holds user, device and org. APNs/FCM stubs: `apns_and_fcm_are_stubs_that_say_not_configured`.
2. Met. RFC 8291 Appendix A: `webpush::tests::rfc8291_appendix_a_vector_matches_byte_for_byte` (encrypt, byte for byte) and `rfc8291_appendix_a_message_decrypts_with_the_user_agent_key`. VAPID ES256 JWT verified against `k`: `vapid_header_is_a_valid_es256_jwt_for_the_endpoint_origin`, `vapid_debug_output_does_not_contain_the_private_key`. Payload only ids, kind and a generic title: `events_map_to_jobs_with_ids_only`, `payload_is_ids_a_generic_title_and_approval_actions`, live test asserts no "rm -rf", "secret" or prompt text.
3. Met. Native consumer tests with fake providers: `an_approval_goes_to_members_of_the_threads_org_only`, `prefs_decide_class_mute_and_quiet_hours`, `gone_subscriptions_are_deleted_and_temporary_failures_ask_for_a_retry`, `web_push_maps_push_service_statuses`, `topic_is_the_task_id_or_a_32_character_hash`, `a_batch_sends_only_the_last_job_per_task`. Live: `an_interrupt_leads_to_one_encrypted_vapid_signed_push_with_ids_only` (exactly one POST, decrypted with the test's key, Topic = task id, VAPID verified), `a_gone_endpoint_is_deleted_and_a_5xx_is_retried_by_the_queue` (503 then redelivery; 410 and 404 delete the subscription), `prefs_class_thread_mute_and_quiet_hours_suppress_deliveries`.
4. Met. The payload has `actions` allow/deny with `interrupt_id` and `option_id`; the live test answers the interrupt with the action's option through `POST /v1/threads/{id}/interrupts/{id}` (200) and checks the same route without a token is 401. No new route. Documented in `notify/mod.rs`.

Deviations and choices to review:

- `RunError{cancelled}` does not notify (a user cancel is not a failure); only `RunError{error}` does (`task_failed`).
- `RunFinished{interrupt}` enqueues `approval_needed` only if the same append batch does not already hold that interrupt; such a job has no option ids, so no actions.
- Quiet hours apply to every class, approvals included (as the criterion reads).
- The live VAPID key: `scripts/hub-test.sh` is outside my allowed files and passes no `VAPID_PRIVATE_KEY`. With `DEV_FIXTURES=1` and no such secret, the hub derives a throwaway key from `ATTACHMENT_SIGNING_KEY` (which the script sets randomly per run). Production never falls back (no secret, no pushes).
- Endpoint validation: https and a public host; `http://127.0.0.1` only with `DEV_FIXTURES=1`.
- Subscribe/unsubscribe do not require `Idempotency-Key` (client-api.md §3 says every POST/DELETE does): they are idempotent per endpoint by construction.
