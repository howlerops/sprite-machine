# M2-008c: thread event_id dedupe + POST /v1/threads dispatch

## Summary

- Thread DO: `POST /internal/threads/{id}/events` accepts `{event_id, envelope}` and acks a repeat within 24 h without a second append (ids in SQLite `event_ids`, recorded only after a successful append); the dev route runs the same handler.
- `POST /v1/threads` (Worker, `threads/routes.rs`): member role, audited `thread.create`, thread id derived from the caller and `Idempotency-Key`; the Thread DO records the host through the init hook, starts the first task (`UserMessage`) and queues a `dispatch` command, which the Thread DO pushes to the Machine DO queue. Replays return the stored answer.
- **Criterion 1 is only half met.** The Machine DO does not pass the frame's `event_id` to the Thread DO, because `ThreadHost::append` (`machines/driver.rs`, outside the allowed paths) does not carry it. See Blocked below.
- Live tests: `thread_do` 7/7, `thread_create` 3/3 (new file), `machine_do` 9/9. The fake runner receives the dispatch after `welcome`.

## Blocked

**Criterion 1, Machine DO half: not met. `blocked_on`: `machines/driver.rs` (`ThreadHost::append` signature) and `machines/tests.rs` (its fake).**

`machines/internal.rs` `WorkerHost::append(host, thread_id, envelope: &Value)` is the one call site, but the frame's `event_id` never reaches it: `driver::event` has the id and passes only the envelope. Passing it needs the trait method to take `event_id`, which is in `driver.rs` (not an allowed path). I did not change `driver.rs` and did not touch `internal.rs`. Once the trait carries the id, the call site becomes `call(..., Some(&json!({"event_id": event_id, "envelope": envelope})))`; the Thread DO side already accepts that shape.

## Spec issues (most literal reading taken)

1. **`event_id` on the internal route is a body field, not a header.** `{"event_id", "envelope"}`, the same shape as a tunnel `event` frame (tunnel.md §3.3). The bare envelope and `{"envelopes": [...]}` forms keep working. Invalid `event_id` is 400; a failed append records nothing, so a corrected retransmit is appended.
2. **`POST /v1/threads` is authorized in `routes.rs`, not `auth/policy.rs`.** `thread_policy` needs a thread id in the path and `auth/**` is not an allowed path, so the route calls the same public primitives (`authenticate`, `Principal::require(Role::Member)`, `audit::record` with `thread.create`) directly. The policy table is the intended home (Discovered work 2).
3. **Shared target dir produced a stale Worker bundle.** With `CARGO_TARGET_DIR=/home/user/.cargo-target-shared`, `hub-test` ran a bundle that did not contain the new create code (`thread.create` absent from `crates/hub/build/index_bg.wasm`); the live test saw a 404 for `POST /v1/threads` that never reached D1. Another worker's `hub.wasm` in the same target dir is the likely cause. All runs above used `/tmp/claude-0/.../scratchpad/target-m2008c`. Discovered work 5.
4. **The thread id is derived, not random.** `th_` + 32 hex of `SHA-256(user_id, key)`. A replay reaches the same Thread DO, so the Thread DO's own `Idempotency-Key` record answers it; no D1 lookup is needed. Different users with the same key get different threads.
5. **`create` reuses the Thread DO idempotency and push.** The `POST /internal/threads/{id}/create` write goes through `write()` like the other writes, so `pushes_commands` already pushes the dispatch to the Machine DO; `do/thread.rs` is unchanged.
6. **No machine check.** `machine_id` is only validated as an id; an unknown or foreign machine id is accepted and the dispatch waits in that Machine DO's queue. Discovered work 3.
