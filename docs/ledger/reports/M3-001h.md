# M3-001h report: connectivity owner for the banner

## Summary

- `connectivity::Connection` is the one owner of the thread `Subscription` and the `Outbox`. It exposes `connectivity()` and `watch_connectivity()` (a `tokio::sync::watch` receiver) for the combined state from `Connectivity::combine`.
- Its methods (`next_persisted`, `reconnect`, `flush`) wrap the owned calls and publish the combined state after each. Publishing uses `send_if_modified`, so a receiver sees only real banner-state changes.
- `enqueue` is passed through (it changes no link). `subscription()` and `outbox()` give read access.
- `Subscription::connect` returns no value when the hub is unreachable, so `Connection` cannot be built while offline at startup (see Discovered work).

## Criteria

1. **A client-core type owns both links and exposes a watch/stream of the combined state; a test drives subscription and outbox state changes and asserts the published banner sequence** — met.
   - `connectivity::Connection` owns the `Subscription` and the `Outbox`; `watch_connectivity()` returns the `watch::Receiver` of the combined state.
   - `banner::the_owner_publishes_the_banner_sequence_as_either_link_changes`: the hub accepts two sockets. The test runs seven steps: connect (Connecting), live (still Connecting), a 202 flush (Online), a transport failure (Offline), socket close (still Offline), outbox back online with the socket still closed (still Offline, nothing published), reconnect and live (Connecting, then Online). It asserts the published states are exactly `[Connecting, Online, Offline, Connecting, Online]` and their banners are `["Connecting...", None, "Offline: ...", "Connecting...", None]`.
   - Without `Connection` the test does not compile. If publishing were skipped after `flush` or `next_persisted`, the `Online` or `Offline` entries would be missing and the test would fail.
