# M2B-010a: hub+tunnel: an interrupt answer typed in the sm TUI is arbitrated by the Thread DO

## Summary
- New up frame `interrupt_answer` (sequenced, exactly-once) and down frame `interrupt_answer_result` (`accepted` / `already_resolved` / `rejected`); spec first (tunnel.md §3.6a).
- Machine DO passes the answer to the Thread DO (`POST /internal/threads/{id}/interrupt-answers`), which reuses `answer_interrupt` (same first-answer-wins, same `approval` command to the runner) with the machine's local user as the actor, idempotent per `answer_id`.
- The shared TUI session no longer applies or sends its own `InterruptResolved`: it sends the answer up, waits for the verdict, and the hub's `approval` command is the only thing that reaches the agent. Loser shows "already answered" and the agent runs the phone's choice.
- Offline (not shared) TUI keeps the local rule, now marked in the spec.

## Spec text added (docs/specs/tunnel.md §3.6a, abridged to the normative paragraphs)
> An answer typed on the runner itself (the `sm` TUI) is **not** an `event`. The runner does not write `InterruptResolved` to its own log or to the agent first; it sends the answer up and waits for the hub, so a phone and the terminal race under one rule.
>
> `interrupt_answer` (up, sequenced) `{thread_id, interrupt_id, answer_id, outcome}`; `outcome` is the `approval` command's union; `answer_id` is chosen by the runner, unique per attempt, and is the hub's idempotency key.
>
> The Machine DO checks the thread is hosted by this machine (else `nack{forbidden}`) and passes the answer to the Thread DO, which resolves it **exactly as it resolves `POST /v1/threads/{id}/interrupts/{interrupt_id}`**: the same first-answer-wins rule, the same checks (unknown interrupt, expired, an outcome the interrupt does not allow), with the actor being the machine's local user (`{kind: "user", id: "local:<machine_id>", name: "terminal", device_id: <machine_id>}`). If the answer wins, the Thread DO appends `InterruptResolved` and queues the `approval` command for the runner **the same way it does for a phone's answer**, so the agent always runs the answer the hub's log names.
>
> The Machine DO answers every `interrupt_answer` it processes with one down frame `interrupt_answer_result {answer_id, status, resolved_by?, message}`. `status` is `accepted`, `already_resolved` (another answer won first; `resolved_by` names it; this is the typed refusal, the equivalent of the phone route's `409`), or `rejected` (`404` unknown interrupt, `410` expired, `400` not allowed).
>
> The result is not sequenced ... If the connection drops before it arrives the runner treats the answer as **not accepted** and shows the interrupt as still open; the log catches up through the `approval` command (§3.5), which is the only way an answer reaches the agent while the session is shared. A runner that gets `already_resolved` shows "already answered", applies nothing, and runs the phone's choice when its `approval` command arrives.
>
> **Offline TUI.** A session that is not registered with a hub (no tunnel; `/rc` never ran or was turned off) keeps the local rule: the first answer to reach the runner's own log wins, and nothing is sent up. This is the only case in which the runner decides an answer itself.

## Limits
- The result frame is not retransmitted: if the socket drops after the hub processed the answer, the TUI times out (10 s) with "the hub has not answered yet" while the hub's `approval` command (reliable) still applies the answer on reconnect. A frame left in the outbox can also resolve after the TUI gave up.
- The real `host.rs` tunnel path is covered by unit tests of `TunnelSink::interrupt_answer` and the live fake-runner test, not by a real `sm` against wrangler (still M2B-010b).
- The local user id is `local:<machine_id>`; pairing it with the paired user's real id stays open.
