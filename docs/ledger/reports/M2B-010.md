# M2B-010: runner: interactive TUI shared with remote devices (`sm --rc`)

## Summary
- `runner::tui`: a pure ratatui state machine (`app`), a buffer renderer (`render`), an event loop over a `Backend` trait (`driver`), the real terminal with restore on exit and panic (`term`), the production session over the real bridge (`session`), and `sm` / `sm --rc [name]` wiring (`host`, small `main.rs` diff).
- The thread is read through client-core (`ThreadSync`); a 409 maps through client-core's outbox state (`AnswerResult::from_intent_state`).
- `autoConnect` (runner::settings) registers at start; otherwise only `/rc` does (`/rc` again stops sharing, the next `/rc` catches up).
- 40 tests in `crates/runner/tests/tui.rs`, including snapshots and a real bridge + acp-mock.

## Design notes and limits
- The runner holds only a machine credential, which the hub's `/v1` routes (subscribe, interrupts) do not accept. So the TUI does not subscribe to the hub. Its log is local: bridge output, plus the `UserMessage` / `InterruptResolved` it writes from hub commands (the hub sends the runner only commands), plus its own answers. Order is the order this runner saw events.
- "First answer wins" is therefore decided at the runner for local vs phone. A phone answer the hub accepted but the runner saw second gets the bridge's `unknown_interrupt`; the hub log may name the phone while the agent ran the local choice. Needs a hub-side rule (see below).
- The tunnel path (`host.rs`: login, `tunnel()`, command forwarding, `thread_open`) compiles and is covered through the `Upstream` seam only; it was not run against a hub or `wrangler dev`. "remote: on" shows connectivity Online after registration, not the live tunnel state.
- `sm` and `sm rc` should not run at once on one machine (same machine tunnel); the TUI keeps its outbox in `<state dir>/tui`.
- The local author is `{kind:user,id:"local",name:"terminal"}`; the hub may want the paired user's id.
