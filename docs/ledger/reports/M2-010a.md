# M2-010a report: task index follow-ups

## Summary

- A soft-deleted thread is `404 not_found` on every `/v1/threads/{id}/...` route: checked in the Thread DO (`ensure_live`, source of truth, also the subscription) and in the Worker gate (`authorize_thread`, D1 `tasks.deleted_at`, covers `subscribe-ticket` and skips the audit row).
- The hourly Cron Trigger now reconciles the task index: hosted threads with no row come first, then the most recently changed, up to 200 per pass. Each Thread DO is asked (`POST /internal/threads/{id}/reindex`) to compare its row with D1 and upsert only when the row is missing or differs.
- `done` has a producer: the last task ended in `RunFinished{success}` and nothing is running or queued; the next prompt clears it. `last_seq`/`updated_at` semantics are documented in client-api §5.2.
- `scripts/hub-test.sh` passes made-up `APPLE_*`/`ANDROID_*` vars to every suite; the live links test asserts 200 plus the body of both documents.

## Notes and limits

- The reconcile compares status, title, machine, agent, workspace, archived and deleted, not `last_seq`/`updated_at` (those lag by design), so a pass does not reorder current threads. It looks at 200 threads per hour; a larger org's older, unchanged threads are reached as newer ones settle (not guaranteed to be complete).
- `DELETE` on an already-deleted thread is now 404 (no second audit row).
- Internal routes (`/internal/threads/...`) still reach a deleted thread so the runner's events and the reindex keep working.
- Removing the `done` meta: threads created before this change have no `finished_ok` flag and read as `open` until their next run ends.
