# M2B-019c: runner tui: no race between a local queued line and a hub-queued phone prompt

## Summary
- In a shared session (`Remote::On`), when a task ends and a local line is queued, the TUI no longer sends it at once. It holds it for a settle window (`SETTLE`, 1.5 s). A hub `prompt` that arrives in the window starts a task and runs first; the local line goes after that task (and after another settle window). A quiet window releases the local line.
- The hub stays the single source of order for phone prompts; the bridge sees one prompt at a time, so it refuses neither.
- No hub, tunnel or spec change: no frame exists for a runner to enqueue a prompt at the hub (the runner has no `prompt`-enqueue frame, only the HTTP client API with device auth), so the "send up to the hub's queue" option would need one. Not shared sessions (no hub) still send at once.

## Acceptance
- A test with a local queued line and a hub-queued phone prompt at task end: neither is refused; both run once in a defined order: MET.
  - `session::a_local_line_and_a_hub_queued_prompt_at_task_end_both_run_once` (real bridge and acp-mock, shared session: after the first task ends the hub's prompt is delivered; the phone task runs, then the local line; each appears once on screen, in that order, no "waiting for the running task" notice, nothing tracked).
  - `a_shared_session_lets_the_hubs_queued_prompt_go_before_the_local_line` (unit: held at task end, released only after the hub's task ends).
  - Both fail with the hold disabled (checked: the local line is sent at once, the bridge refuses the phone prompt, the phone task never runs).

## Ordering rule chosen
Settle window (the first hint option), because the existing frames give the runner no way to enqueue at the hub. Rule: in a shared session, after a task ends the TUI sends its next queued local line only once no task has started for `SETTLE` (1.5 s). Hub-queued prompts that arrive earlier go first, in the hub's order; local lines then follow in typed order. Unshared sessions send at once.

Known limit: if the hub's prompt takes longer than the window to arrive (slow link), the old race remains; the existing fallback still applies (a refused local line is queued again, never lost; the bridge refuses the hub's prompt in that case). The proper fix is a hub-ordered path for local lines (see Discovered work).
