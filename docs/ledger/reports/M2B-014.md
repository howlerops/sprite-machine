# M2B-014 report: presence + reconnect notifications on the phone

## Status: DONE

## Summary

- A machine that comes back online while commands are queued for it (its outbox has thread rows) sends one `machine_back` push per comeback to each user of the org, ids only (`kind`, `title`, `thread_id`). The Machine DO enqueues it from the presence change in `do/machine.rs`.
- Debounce: at most one machine-back push per machine per `MACHINE_BACK_DEBOUNCE_MS` (60 s, leading edge, the comeback inside the window is dropped). The debounce is one JSON value in the Machine DO storage, so the window survives eviction. Injected-clock native tests in `notify/presence.rs`.
- New notification class `machine_back` (prefs, default on, one line in spec §5.8). Approvals are unchanged: M2-011 already pushes `approval_needed` on Interrupt.

## Acceptance criteria

1. **Met.** A machine with queued work comes back, one push. Live: `a_machine_back_with_queued_work_sends_one_push_with_ids_only` (the prompt waits in the outbox while offline; on the runner's hello exactly one push arrives, with `kind` `machine_back`, `thread_id`, the generic title, and no prompt text).
2. **Met.** Presence flapping is debounced, one push per machine per 60 s window.
   - Live: `a_quick_reconnect_within_the_window_sends_no_second_push` (socket drop and reconnect with the prompt still unacked: no second push). Without the debounce this comeback would push again, so the test fails without the change (reasoned, not run as a mutation).
   - Native, injected clock: `notify::presence::tests::a_flapping_machine_sends_one_push_per_window`, `the_first_return_is_admitted_and_the_window_holds_the_next_one_back`, `a_clock_that_went_backwards_does_not_block_forever`.
   - No push when nothing is queued: `a_machine_back_with_nothing_queued_sends_no_push` (live) and `a_reconnect_with_nothing_queued_does_not_use_up_the_window` (native).
3. **Not duplicated (by design).** "Needs an approval" is pushed by M2-011 on Interrupt (`jobs_for`, `approval_needed`). Nothing changed there.
4. **Out of scope.** The "waiting for <machine>" UI is WEB-002 and M2B-013.

Also covered: `a_machine_back_goes_to_each_user_once_not_once_per_device` (live): two subscriptions of the same user get one push in total.

## Decisions and deviations to review

- **Title and payload.** The title is generic, "Machine back online". The leader's suggested "<machine name> is back" is not used: a machine name is user text and the plan allows only ids and a generic title. The payload has `thread_id` but no `machine_id`. Adding a `NotifyJob` field would change the struct literals in `notify/tests.rs`, which is outside this item's files.
- **Per user.** A user with several devices gets one push on the first subscription in `store::targets` order. The device is not chosen.
- **Debounce.** Leading edge: a comeback within 60 s of the last admitted one is dropped, not deferred. A deferred push would need an alarm.
- **Failure mode.** A storage read or write error sends nothing for that comeback.
- **Commit subject.** The subject "machine-back push, debounced" is the one the brief asked for.
- **Test code.** `presence_notify.rs` copies about 600 lines of helpers from `machine_do.rs` and `notify.rs` (pruned to what it uses). The copies should move to a shared test module.
