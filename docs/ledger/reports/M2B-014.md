## Acceptance criteria

1. **Not met.** Push when a machine with queued work comes back. Only the decision exists. No push is sent and nothing calls `machine_back_thread`.
2. **Met (unit level).** Debounce, at most one "machine back" push per machine per window, constant `MACHINE_BACK_DEBOUNCE_MS`, native test with injected clock: `notify::presence::tests::a_flapping_machine_sends_one_push_per_window` (plus `the_first_return_is_admitted_and_the_window_holds_the_next_one_back`). Not yet used by any caller.

## Blocked on (decisions and scope the leader needs to settle)

1. **Notification class.** `Kind` (`notify/job.rs`) drives the queue message, the payload and the prefs. A machine-back push needs a fourth kind, e.g. `machine_back`, with a title and urgency, plus a prefs class (`notify/prefs.rs`, `Kind::ALL`) and the §5.8 class list in `docs/specs/client-api.md`. Product question: default on or off?
2. **Recipient job shape.** One job per machine (not per thread), so each user gets one push. Its `thread_id` is the first thread from the outbox. `process_job` resolves org from that thread, which already works.
3. **Call site (`do/machine.rs`).** In `process`, for a `Queued::Frame`, compare `state().presence` before and after `handle_text`. On a change to `online`, read the outbox's thread ids (`core.store().outbox()`, the same call `dump` makes) and call `machine_back_thread`. The outbox keeps commands until the runner acks them, so the rows are still there after hello.
4. **Debounce persistence.** The Machine DO is evicted when idle, so an in-memory `MachineBackDebounce` would reset and let a flap send again. Store its JSON in DO storage (one key per machine) and load it before each decision. This is a design choice, so I did not make it.
5. **Debounce semantics (proposed).** Leading edge: a comeback inside the 60 s window is dropped, not deferred. A deferred (trailing) push would need an alarm.
6. **Live test.** `crates/hub/tests/presence_notify.rs` plus a `[[test]] presence_notify` entry with `required-features = ["live"]`. It needs a fake runner over the tunnel with a queued command and a fake push service.
