# M2B-004e: runner: start the sleep watcher at startup with a logind delay inhibitor; macOS sleep watcher (IOKit) implemented

## Summary

`sm run --hub <url>` is the runner start path. It calls `sleep::spawn(client.sleep_hint())` before `TunnelClient::run`. The `SleepWatcher` trait now carries power events (`WillSleep` / `Resumed`) and a delay on sleep (`take_delay` / `release_delay`). `sleep::forward` writes the hint and only then releases the delay. On Linux the delay is a logind `Inhibit("sleep", ..., "delay")` fd. On macOS, `sleep/macos.rs` is an IOKit `IORegisterForSystemPower` watcher: WillSleep is hinted then acknowledged with `IOAllowPowerChange`, and CanSystemSleep is allowed at once. The macOS decision logic is platform-independent and tested on Linux. The macOS code is not compiled here.

- `crates/runner/src/main.rs`: `sm run --hub <url>` (`run_tunnel`). - `crates/runner/src/sleep/linux.rs`: `Manager.Inhibit` added to the proxy. `take_delay` stores the returned fd, `release_delay` drops it. `PrepareForSleep(true)` maps to `WillSleep` and `(false)` to `Resumed`.
- `crates/runner/src/sleep/macos.rs`: hand-declared FFI (IOKit `IORegisterForSystemPower`, `IOAllowPowerChange`, `IONotificationPortGetRunLoopSource`; CoreFoundation `CFRunLoopGetCurrent`, `CFRunLoopAddSource`, `CFRunLoopRun`, `kCFRunLoopDefaultMode`). A run loop thread owns the callback. `kIOMessageSystemWillSleep` = `0xE0000280`, `kIOMessageCanSystemSleep` = `0xE0000270`.
- `crates/runner/tests/sleep_hook.rs`: 7 tests (fake watcher with a recorded delay, recording hint, `power_action`, Linux no-bus error, fake-hub end-to-end).
- `Cargo.toml` and `Cargo.lock`: unchanged. The macOS FFI needs no crate, so no `io-kit-sys` / `core-foundation` dependency was added.

## Acceptance criteria

1. **Partly met.**
   - The start path is `run_tunnel` in `main.rs`. It calls `sleep::spawn(client.sleep_hint())` and then `client.run(...)`, in that order.
   - The Linux watcher takes `Inhibit(sleep, delay)` and holds the fd. On `PrepareForSleep(true)` it writes the hint, then closes the fd. On `(false)` it takes the inhibitor again.
   - The ordering is checked with a fake watcher and a recording hint in `the_hint_is_written_before_the_delay_is_released` (log: `take, hint, release, take, hint, release`). `a_refused_delay_still_gets_the_hint_before_the_sleep` checks that a refused inhibitor still gets the hint.
   - Not covered by a test: the real logind `Inhibit` call and the spawn-before-run order inside `run_tunnel`. Both need a real D-Bus or a test seam in `main.rs`. No test would fail if the `sleep::spawn` line were moved below `client.run`.
   - `each_pre_sleep_notification_sends_presence_asleep` checks the hint reaches a fake hub as `presence{asleep, os_sleep}` through the forwarder.
2. **Met in code, not compiled.**
   - `sleep/macos.rs` implements the IOKit watcher as described above. WillSleep goes to the tokio side, which calls `release_delay`, which calls `IOAllowPowerChange`. CanSystemSleep is allowed in the callback.
   - The decision logic is `power_action` in `sleep/mod.rs`. Tests on Linux: `can_system_sleep_is_allowed_at_once_without_a_hint`, `will_system_sleep_is_hinted_and_then_allowed`, `other_power_messages_are_ignored`.
   - The macOS build has not been run. The apple target is not installed and was not installed, per the instructions. The FFI declarations were written from the IOKit headers without a compiler check and need the macOS CI job (after CI-001).

## Design notes and limits

- The delay is a trait method (`take_delay` / `release_delay`), not a separate type. Linux holds the fd, macOS holds nothing and uses the notification id from the pending WillSleep.
- `CanSystemSleep` is allowed without a hint. A WillSleep with no live tunnel still releases after the hint's 1 s wait (`SleepHint::asleep`).
- The mac `Context` is leaked (`Box::leak`), so the callback pointer stays valid for the process.
- `run_tunnel` advertises no harnesses and no spawn modes. It keeps the tunnel up only. The sidecar bridge is not wired to the sink or command source, so nothing executes commands yet.
- `sm run` has no test of its own. It needs a stored login and a fake hub.
