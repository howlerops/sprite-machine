# M3-002d report: an idle outbox follows the live subscription

## Summary

- The branch was not at `v2` and had no commits of its own, so it was reset to `v2` first.
- `docs/specs` (client-api.md and the rest) say nothing about banner or connectivity semantics, so the simplest rule applies and is documented in `Connection::state_of`: an outbox that is still `Connecting` (no HTTP answer or failure since load) and has nothing queued has no opinion, so the combined state follows the subscription. A queued, unanswered intent makes the outbox count as `Connecting` again; an answer (`Online`) or a transport failure (`Offline`) always counts.
- `Connection::enqueue` now publishes the combined state, because queuing an intent changes whether the outbox has an opinion (live and idle is online, live with an unanswered send is connecting, as before).
- `Outbox` itself is unchanged apart from a doc comment; `Connectivity::combine` is unchanged.

## Files changed

- `crates/client-core/src/connectivity.rs`: `Connection::state_of`, used by `new`, `publish`; `enqueue` publishes.
- `crates/client-core/src/outbox.rs`: doc comment on `Outbox::connectivity` only.
- `crates/client-core/tests/banner.rs`: two sequence tests updated to the new states, one new test.
- `crates/client-gpui/tests/shell.rs`: `the_banner_follows_a_client_core_connection` now expects the banner hidden when live and idle, and "Reconnecting..." after an unanswered enqueue. The two window tests `after_sign_in_the_banner_follows_the_sessions_own_connection` and `a_stored_session_opens_the_link_at_launch_and_signing_out_closes_it` also encoded the old behaviour (waited for "Reconnecting..." with a live idle link) and were changed to expect no banner; the first now polls for the cancel POST before the final banner check.
