# M1A-006b report: runner bridge (ACP client → mapping → EventSink; CommandSource)

## Summary

- `sidecar::bridge::Bridge<S: EventSink, C: CommandSource>` owns one `AcpClient`, one `AcpTurnMapper` per thread, the `Reattacher` and the `Store`. It turns hub commands (prompt, dispatch, approval, cancel) into ACP calls and ACP traffic into TurnEvents on the sink.
- Commands are deduplicated by idempotency key through `Store::commit_down_frame`; failures go out as `command_result` (`capacity`, `unknown_thread`, `unknown_interrupt`, `invalid`). Permission requests become Interrupts, are stored with a TTL, and expire on a timer.
- `fs/*` goes to `Workspace`, `terminal/*` to `Terminals` (Activity tee goes to the sink inside the current run). `emit_user_message` (default false) is set by the tracer adapter.
- `sidecar::tracer::{run, BridgeConfig}` is now a thin adapter over the bridge (no stub header); `tracer_mapping.rs` is deleted.

## API for M2B-004 (tunnel client)

```rust
pub trait EventSink: Send + Sync + 'static {
    fn send(&self, envelopes: Vec<Envelope>) -> impl Future<Output = Result<(), SinkError>> + Send; // seq 0, one call = one step, in order
    fn command_result(&self, failure: CommandFailure) -> impl Future<Output = Result<(), SinkError>> + Send; // CommandFailure{idempotency_key, code: CommandErrorCode, message}
}
pub trait CommandSource: Send + 'static {
    fn next(&mut self) -> impl Future<Output = Option<IncomingCommand>> + Send; // cancel safe; None = tunnel client shut down
    fn processed(&mut self, seq: u64) -> impl Future<Output = ()> + Send;       // called after the key + seq are committed and the effect applied/rejected: ack now
}
pub struct IncomingCommand { pub seq: u64, pub idempotency_key: String, pub command: Command }
```

- Construct with `Bridge::connect(config, reader, writer, store, ids, sink, commands)` or `Bridge::spawn(config, tokio::process::Command, ...)`, then `bridge.run().await`. `Config::new(machine_id, agent_id, cwd)` plus `emit_user_message`, `approval_ttl`, `expiry_check_interval`, `max_running_tasks`.
- The bridge calls `commit_down_frame(seq, Some(key))` itself, so the tunnel client must not, and must not ack before `processed(seq)`. The sink should persist to the outbox (`enqueue_outbound`) and send `command_result` as an up frame. An unknown command `kind` fails to parse in the tunnel client, which must send `unsupported` itself (the typed `Command` cannot represent it).
- Ids: `UlidIds` (production), `SequentialGenerator` (tests). In-memory: `MemorySink`, `MemoryCommands`/`CommandFeed`.

## Decisions

- One running task per thread: a second `prompt` gets `command_result invalid`. The ACP client's own pending queue is never used because the hub owns the queue (answers M1A-003d: nothing is queued below the bridge, so no task runs after a cancel).
- `prompt` for a thread the bridge has never seen uses `Config::cwd` and `agent_id` (the tracer needs it). `dispatch` uses `workspace.path` as cwd and `agent` as harness; `spawn: worktree` and `permission_mode` are ignored.
- Cancel: drains pending updates, sends `session/cancel` (the client answers waiting permissions `cancelled`), then emits `mapper.on_cancel` with the `runner` actor. Late stop reasons for ended tasks are ignored.
- Expiry: live interrupts are expired by the bridge's own mapper; stored interrupts without a live request (left by an earlier process) go through `expire_overdue_interrupts` at startup and on the timer.
- Terminal Activity is forced into the task's current run; output teed while paused is held and sent after the resume `RunStarted`.
- File parts of a prompt are sent to the agent as ACP `resource_link` blocks (no download; "attachments later").

## Spec issues

- turn-event.md §5 rule 6 / client-api.md §6: the runner never emits `InterruptResolved` for an accepted approval, so a runner-only log fails `SequenceValidator`. Tests play the hub. Worth a sentence in the spec for golden-test authors.
- tunnel.md §3.5 `dispatch.workspace.spawn` and `permission_mode` have no defined runner behaviour yet.
