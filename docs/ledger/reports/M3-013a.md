# M3-013a: notifications and hub links in the desktop shell

## Summary

`AppShell` now owns a `Notifier`, a `ToastSink`, an `EventQueue` and a `NotifySettingsView`.

- **Inbox to notifier.** `InboxView` counts the lists its model takes (`lists_applied()`). The shell observes the inbox and acts when that counter moves. The first applied list is a baseline (`Notifier::seed`); later lists go to `observe_all`. A filtered, searched or show-archived list is ignored, because it holds threads the user has not seen change. The baseline resets when the session ends.
- **Focus.** The open thread is the focused one, except while the window is in the background. `AppShell::set_window_active(bool)` is fed by a window-activation observer. Open and close of a thread, and sign-out, re-sync the focus.
- **Toasts and clicks.** `AppShell::pump_notifications(window, cx)` flushes the sink into the window and drains the `EventQueue`; `NotifyEvent::Open{thread_id}` goes to `open_inbox_thread`, which calls `open_thread` with the row's workspace. It runs after each applied list and on a 100 ms timer. `toasts_shown()` and `notify_events()` are exposed for tests.
- **Deep links.** `AppShell::open_url(url, cx) -> bool` runs `hub_link_thread` against the session's hub and opens the thread. Other URLs return false and do nothing.
- **Settings.** `NotifySettingsView` is mounted inline on the Settings page (`notify-settings`). Prefs live in `notifications.json` next to the other preferences (temp dir when the shell has no prefs path).
- **Failed status.** `inbox::Status::Failed`, parsed from the string `failed`. It sits in the Done section, has the row label "Failed" (new key `inbox-filter-status-failed`), and its query value is `failed`. A failed transition notifies.

## Criteria

1. Seed, one toast, no repeat: `a_thread_moving_to_needs_you_notifies_once_and_the_first_fetch_is_only_a_baseline`. It counts `toasts_shown()` and also checks one notification in the window.
2. Open thread quiet, background notifies: `the_open_thread_does_not_notify_unless_the_window_is_in_the_background`.
3. Open event: `a_click_on_a_notification_opens_its_thread`. The fake hub sees the subscribe to `th_b`.
4. Hub link: `a_hub_link_opens_its_thread_and_other_urls_are_ignored`. Other hosts, paths and junk are refused.
5. Settings: `the_notification_settings_are_on_the_settings_page`.
6. Failed: `a_failed_status_is_its_own_status_and_sits_with_done` (tests/inbox.rs) and `a_failed_transition_notifies`. No existing inbox test changed.

  detail: >
    client-api.md section 5.2 lists the thread status as idle|running|needs_you|done, and

    Until then a failed run shows as done. Decide whether to add "failed" to section 5.2 and to
    api_status (and the status= filter), or keep the fold. Not changed here: hub and spec are out
    of this item's paths.
  depends_on: []

  lane: client
  title: Refresh the inbox on a timer or from a hub push
  detail: >
    The inbox fetches only on target change, filter change, search and after writes. Notifications
    therefore fire only when a refresh happens. A periodic refresh (or a push from the hub) is
    needed for useful desktop notifications. The shell side is ready: any applied list is observed.
  depends_on: []

  lane: client

    list after it is closed, if its status moved while open and the list status differs.
  depends_on: [M3-013a-hub-failed-status]
