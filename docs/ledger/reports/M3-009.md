# M3-009: client: plan view + cost/context meters

## Summary

Two stateless task-view widgets with plain-Rust models behind them.

- `PlanModel::from_thread(&ThreadView)` takes the latest `Activity{plan}` (last task that has
  one) and gives rows with status (pending / in progress / completed), priority and an a11y
  label, plus "n of m done". `render_plan` draws it (empty state included).
- `UsageTracker::observe(&ThreadView)` turns the `usage` state document into a `UsageModel`:
  per-turn and cumulative tokens, per-turn and cumulative cost, and context percent.
  `render_usage` draws it. When the window size is unknown the percent is hidden and a
  "Context window unknown" line shows; unknown cost shows "Cost unknown"; with no usage at all
  the widget shows only its title.
- Strings are in the new `locales/en/task.ftl` (own catalog, `OnceLock`, same pattern as
  compose/approval).

## Criteria with evidence

- Plan widget shows latest entries with status and priority, live: `the_plan_updates_as_successive_plan_activities_arrive`
  (snapshot, replacing snapshot, JSON-patch) and the headless
  `the_plan_widget_redraws_rows_when_the_plan_changes` (find_all on `plan-widget-row` labels
  change between frames). `the_latest_task_with_a_plan_wins` covers multi-task.
- Usage widget: per-turn and cumulative tokens and cost, context percent when known, hidden or
  unknown when not: `the_tracker_reports_per_turn_and_cumulative_tokens_and_cost`,
  `context_percent_is_known_only_with_a_window_size`, `unknown_cost_and_window_stay_unknown`,
  headless `the_usage_widget_shows_figures_and_hides_the_percent_when_the_window_is_unknown`.
- Plain-Rust models with unit tests plus headless view tests: above. Each test fails without the
  change: the tests import the new modules, so they do not compile without them.
- All strings from Fluent with a catalog test: `every_string_id_in_the_code_is_in_the_catalog_and_every_catalog_id_is_used`
  (scans plan.rs and usage.rs both ways).

## Hookup (for the shell/transcript owners; those files were not touched)

Keep a `PlanModel` and a `UsageTracker` next to the `ThreadView`. After each
`ThreadView::apply`: `plan = PlanModel::from_thread(&thread)` and
`usage = tracker.observe(&thread)`, then `cx.notify()`. Draw `render_plan(&plan)` and
`render_usage(&usage)` in the task header or side area. The transcript's own plan rows
(`task/tools.rs`) remain and are unaffected.

## Discovered work

```yaml
- id: usage-token-counters
  title: usage state has no token counters
  detail: >
    The usage document is {context_used, context_size, cost, turn_cost?}. "Tokens" here are
    derived from context_used growth (per turn since the turn's first task event, cumulative
    as the sum of increases, never decreasing on compaction). True input/output token totals
    per turn need new fields (for example turn_tokens, total_tokens) in turn-event.md section
    4.6 and the ACP mapping.
  area: protocol, spec
- id: usage-history-in-client-core
  title: move UsageTracker logic into client-core
  detail: >
    Per-turn figures need history that ThreadView does not keep (only the latest usage
    document). UsageTracker lives in the GUI crate and only sees states at observe() time, so a
    replay applied in one batch before the first observe() reports the whole context as one
    turn. A client-core view model that records usage at each task start would remove this.
  area: client-core
- id: usage-turn-cost-field
  title: producers should send turn_cost
  detail: >
    The spec lists turn_cost? as optional; the ACP mapping does not emit it. The tracker derives
    it from cost minus the cost at turn start when absent (same currency only).
  area: protocol mapping
- id: task-view-hookup
  title: place plan and usage widgets in the task view
  detail: >
    Shell/task owners must call PlanModel::from_thread and UsageTracker::observe after each
    apply and render the widgets (see Hookup). Not done here per path limits.
  area: client-gpui shell, task/transcript.rs
- id: shared-target-dir-doctest-race
  title: shared cargo target dir can break doctests
  detail: >
    Concurrent worktrees sharing CARGO_TARGET_DIR can replace rlibs mid-run, failing the
    doctest step with "extern location ... does not exist". A rerun fixes it.
  area: tooling
```
