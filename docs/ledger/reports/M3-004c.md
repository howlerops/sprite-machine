# M3-004c: keep the capped mode on reopen

## Summary
- Runner: when a thread's session starts, its effective (capped) permission mode is written to `sessions/<thread>/permission_mode`. An idle-close reopen reads it and caps it again by the machine's local mode, instead of using the local mode.
- A thread with no record (stored before this change) still reopens in the local mode.
- tunnel.md "Permission mode cap" reopen sentence updated.

## Files changed
- crates/runner/src/server/mod.rs (`PermissionMode::save` / `load`, record name)
- crates/runner/src/server/router.rs (`start_session` records the mode; `reopen` reads it)
- crates/runner/tests/server_mode.rs (`a_thread_started_in_plan_on_a_default_machine_is_reopened_in_plan`)
- docs/specs/tunnel.md (reopen sentence only)

## Verify output
- `cargo test -p runner --test server_mode`: 30 passed, 1 ignored (pre-existing), exit 0
- `cargo test -p runner`: all suites ok, exit 0
- `cargo clippy -p runner --all-targets -- -D warnings`: exit 0

## Criterion
- Met: "A thread started in plan on a default machine is reopened in plan after an idle close". Test `a_thread_started_in_plan_on_a_default_machine_is_reopened_in_plan` dispatches with `plan` on a `Default` machine, closes the idle session with `server::close_session`, prompts again, and asserts the second agent process receives `session/set_mode:plan` before `session/prompt`.
- The test fails with the reopen change reverted (`let mode = self.ctx.permission_mode;`): the assertion at the `set_mode:plan` position panics. The fix was restored afterwards.
