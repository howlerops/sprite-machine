# M3-009a: desktop task view: show the plan and usage widgets for the open thread

## Summary

The open thread's plan and usage widgets now sit beside the transcript, and they update when new
events arrive.

- `SessionLink` (link thread) computes both figures for each snapshot. `ThreadSnapshot` gained
  `plan: PlanModel` (from `PlanModel::from_thread`) and `usage: UsageModel`.
- The `UsageTracker` lives on the link thread, inside `Core`, and is reset when a thread is opened.
  `publish_snapshot` calls `observe` on every publish. Each applied event is followed by a publish,
  so every state is seen once.
- `AppShell` keeps the figures from the last snapshot. `render_thread` lays the pane out next to a
  260 px side column that draws `render_plan` and `render_usage`.
- Empty states: a thread with no plan shows the plan widget's "No plan yet". A thread with no usage
  shows the usage widget's title only. Neither widget is hidden.

### Why the tracker is on the link thread, not the UI side

The tracker needs every applied state. The UI only receives the latest snapshot through a `watch`
channel, which keeps one value. If several events arrive before the UI reads, the intermediate
states are lost. The tracker would then miss task starts (which open a new turn) and intermediate
usage growth, so per-turn and cumulative figures would be wrong. The link thread sees each applied
event, so it is the only place where the tracker is correct. Only the plain-data figures cross to
the UI.

## Files

- `crates/client-gpui/src/shell/link.rs`: `ThreadSnapshot.plan` and `.usage`; `Core.usage`
  (`UsageTracker`), reset in `open_thread`; `publish_snapshot` observes and compares plan and usage
  as well as cards.
- `crates/client-gpui/src/shell/view.rs`: `plan` and `usage` fields on `AppShell`, set in
  `apply_snapshot` and reset when a different thread opens; `render_thread` draws the pane and the
  side column (`render_plan`, `render_usage`).
- `crates/client-gpui/tests/shell.rs`: fake hub gets `pushed` frames, which the subscribe socket
  sends after `live` (`push_live`); helpers `labels_shown`, `plan_frame`, `usage_frame`; two window
  tests (below).

`task/**` and `approval/**` were not changed (the widgets already existed).

## Criteria with evidence

1. **Opening a thread with plan and usage shows both widgets beside the transcript.** Met.
   `an_open_thread_shows_its_plan_and_usage_and_follows_new_events` opens `th_a`, whose replayed
   events include a plan and a usage state. It checks the summary "0 of 2 done", the two rows
   (`Add route: In progress, High priority`, `Add test: Pending, Medium priority`), "Total: 10k
   tokens", "This turn: 10k tokens" and "Total: 0.01 USD". The layout is in `render_thread`.
2. **The widgets update when new events arrive.** Met, in the same test. After the fake hub pushes a
   new plan (first task completed, second in progress) and a new usage state (30,000 tokens, 0.03
   USD), the test sees "1 of 2 done", the new row labels, "Total: 30k tokens", "This turn: 30k
   tokens" and "Total: 0.03 USD".
3. **Threads without plan or usage show the empty states.** Met.
   `a_thread_without_a_plan_or_usage_shows_the_widgets_empty_states` (fixture `hub_with_a_diff`):
   "No plan yet" is shown, there are no plan rows, the usage title "Usage" is shown, and none of
   the figure or context lines appear. Choice: show the empty states rather than hide the widgets.
4. **Tests fail without the change.** Met. The new window tests look up ids that did not exist in
   the shell before (`plan-widget-summary`, `usage-widget-total-tokens` and so on). The mutation
   check above shows the update path is exercised.

## Not covered / known limits

- Per-turn tokens at open: the link's tracker observes the whole restored thread from the cache in
  one step, so for a thread reopened from the cache "This turn" equals the total. This is the
  existing limit recorded in M3-009 (`usage-history-in-client-core`). It is recorded again below as
  `M3-009a-replay-turn`.
- The widgets are fixed to a 260 px column; no responsive layout was added.
