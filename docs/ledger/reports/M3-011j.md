# M3-011j: shell tests wait on conditions

## Summary

- `the_banner_follows_a_client_core_connection` had no sleeps of its own, but it read the banner once after each state change with no wait. The banner follows a watch feed, so a single read can see the previous state. Each check now goes through `wait_for_connection_banner`, a deadline-bounded poll (400 x 25 ms) that matches the expected text.
- Other fixed sleeps in `tests/shell.rs` used as synchronization were converted or removed (list below).
- Reset before starting: the branch had no commits of its own and was behind `v2`, so it was reset to `v2` (15ea172).
- Root cause of the one-time flake was not reproduced. The test now waits on the condition it asserts, which removes the single-read race, but the exact cause is unconfirmed.

## Files

- `crates/client-gpui/tests/shell.rs`: new helpers `connection_banner` and `wait_for_connection_banner`; target test switched to them; sleep sites listed below.
- `docs/ledger/reports/M3-011j.md` (this file).

No changes under `src/`, `apps/`, `packages/` or `main`.

## Sleep sites in tests/shell.rs

| Where | Before | After |
|---|---|---|
| `the_banner_follows_a_client_core_connection` (5 banner reads) | single read, `assert_eq!` | `wait_for_connection_banner` (deadline poll) |
| `browser_follows` (async poll for the opened URL) | unbounded loop, 10 ms sleep | same loop with a 10 s deadline and a panic message |
| `after_sign_in_the_banner_follows_the_sessions_own_connection` (cancel reaches hub) | hand-written 400 x 25 ms loop | `wait_until_true` |
| `quick_allow_on_a_row_answers_and_does_not_open_its_thread` | `sleep(200ms)` then assert no subscription | sleep removed. The shell never called `link.open_thread` (checked by `open_thread_id() == None` right after the answer arrived), so the list cannot change. |
| `the_link_follows_the_thread_the_screens_open`, pre-open check | `sleep(200ms)` then assert empty | sleep removed. The exact-list check `["th_a"]` that follows already fails if a placeholder subscription was ever made. |
| `the_link_follows_the_thread_the_screens_open`, "already followed is not a new subscription" | `sleep(200ms)` then compare count | the no-op `open_thread("th_b")` is followed by a real switch to `th_a`. The link handles commands in order, so waiting for `["th_a","th_b","th_a"]` is a barrier: an extra subscription from the no-op would appear before it. |

Remaining `sleep` calls are all inside deadline-bounded polls (`wait_until`, `wait_for_banner`, `wait_for_label`, `wait_for_shown`, `wait_until_true`, `wait_for_inbox`, `wait_for_connection_banner`, `browser_follows`).

## Notes

- The flake (one failure in a full run, noted in M3-011f) was not reproduced in 21 runs of the suite. Its cause is not confirmed. The likely candidate is a banner read racing the watch feed, which the new wait covers. The `connection.connectivity()` state asserts in that test were left as direct asserts, since the state is set synchronously on the test thread.
- Two absence checks now rely on ordering arguments, not a timed quiet window. The link's FIFO command order is what makes the "already followed" barrier valid.

## Discovered work

```yaml
- id: M3-011j-D1
  title: "tests: a link barrier so absence checks do not need a timed window"
  why: "The link runs on its own thread and exposes no way to wait until it has processed the commands sent so far. Absence checks (no subscription was made) therefore either rely on an ordering argument or a fixed sleep. A test-only barrier on the link (for example, a Command::Sync that replies on a channel) would let tests wait for a known point instead."
  lane: client
  files: [crates/client-gpui/src/shell/link.rs, crates/client-gpui/tests/shell.rs]
```
