# M2B-005b: `sm logout` / `sm status`; run mode uses stored credentials; Linux persistence decision

## Summary

- `sm logout` wipes the credential from the keychain and the file; `sm status` prints hub, machine id and `credential: present|none`, never the credential. Both in `login/account.rs`, wired in `main.rs`.
- Linux persistence decision: the `0600` file is the persistence path. `from_env` no longer uses keyutils on Linux (kernel memory, lost at reboot), so the `keyring` Linux dependency is gone. macOS keeps the Keychain in front of the file.
- Run mode: `sm rc` loads the stored hub, machine id and credential and dials the tunnel with them; a fake-hub test checks the upgrade path, the `Authorization` header and the `hello` frame.
- Literal `KeychainCredentials::from_env` call site is not used: `server::run` (out of scope) wraps the `CredentialStore` it is given. Same store, same behaviour; see criterion 2.

- `crates/runner/src/login/mod.rs`: module declaration and re-exports; module docs updated.

## Acceptance criteria

1. `sm logout` wipes the credential (keychain and file); `sm status` prints hub, machine id and presence, never the credential: MET.
   - `logout_wipes_the_keychain_and_the_file` (keychain secret and leftover file both gone; output has the machine id, not the credential).
   - `logout_when_not_logged_in_says_so`.
   - `status_shows_hub_machine_and_presence_but_never_the_credential`.
   - `sm_status_and_sm_logout_use_the_forced_credential_file` (real `sm` binary: `status`, `logout`, `status` shows none, `status extra` is a usage error).
2. The run path builds the tunnel from the stored hub URL and machine id, with the stored credential: MET in substance, NOT literally from `KeychainCredentials::from_env`.
   - `sm_rc_dials_the_stored_hub_as_the_stored_machine_with_the_stored_credential`: the real `sm rc` binary, a fake hub on loopback; the test checks path `/v1/machines/mch_run/tunnel`, `Authorization: Bearer <stored credential>`, and that the first frame is `hello`.
   - Deviation: `main.rs` passes `CredentialStore::from_env()` in `server::Options`, and `server::run_with` (`server/mod.rs`, outside this item's files) wraps it in `KeychainCredentials::new`. `KeychainCredentials::from_env` is that same call with the same store. To make the call site literal, `Options.credentials` must take a `KeychainCredentials` (see discovered work).
3. On Linux the report states the persistence path and why keyutils alone is not enough: MET.
   - Persistence path: `$XDG_CONFIG_HOME/sm/credential.json` (else `~/.config/sm/credential.json`), mode `0600` in a `0700` directory, written through a temp file and rename. `SM_CREDENTIAL_FILE` forces the same kind of file.
   - Why keyutils is not enough: keyutils keeps keys in kernel memory. The keyring crate's own docs say the credential lives in the user's persistent keyring, which expires after `/proc/sys/kernel/keys/persistent_keyring_expiry` (a few days by default, reset on each `Entry::new`). It does not survive a reboot. The previous code wrote the credential only to keyutils on Linux, so after a reboot `sm rc` would report "not logged in".
   - Test: `on_linux_the_login_persists_in_the_0600_file_across_processes` (`sm login` writes a `0600` file under `XDG_CONFIG_HOME`; a separate `sm status` process still finds it). This test would fail on the previous code, which wrote to keyutils on Linux.
   - Behaviour change for existing Linux logins: a credential stored in keyutils before this change is not read any more. Those machines show "not logged in" and must run `sm login --hub <url>` once.

## Notes

- `sm logout` wipes locally only. The hub keeps the machine registered until an admin revokes it (or the machine calls `DELETE /v1/devices/self`). See discovered work.
- No test touches the real user keychain or home directory. The binary tests set `HOME` and `XDG_CONFIG_HOME` to temp dirs and `SM_CREDENTIAL_FILE` where a file is forced.
