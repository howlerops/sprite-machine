# WEB-003: composer with attachments, Allow/Deny, Stop, offline outbox

## Summary
- The thread view has a composer (text, Attach picker, Camera input, Send, Stop). Prompts go through an outbox (`sm.outbox` in localStorage, one `Idempotency-Key` per intent) so they survive offline and a reload; queued prompts show as removable chips.
- Files are uploaded to the signed URL from `POST /v1/attachments` (client refuses >20 MB) and sent as `file` parts.
- Open approvals get Allow/Deny buttons (from the interrupt's own options); a 409 shows "This was already resolved by <who>."; Stop cancels the running task.
- Test harness fix: `web/tests/helpers-hub.sh` now builds the hub wasm into a per-worktree target dir (same key as `scripts/hub-test.sh`); without it another worktree's build replaced the served hub and fixtures 404'd.

## Acceptance criteria
1. Composer sends prompts; pending chips while a task runs, removable: met. `a prompt is sent; while a task runs it shows as a removable pending-task chip`, `an idle thread starts the prompt...`, `an empty message is not sent`.
2. Attach via picker or camera, uploaded to signed URL, <=20 MB, sent as FileParts: met. `a picked file is uploaded to the signed URL and sent as a file part` (bytes and type read back from the part URL), `the camera input takes a photo and sends it with no text`, `a file over 20 MB is refused before any upload...`.
3. Allow/Deny on Interrupt{approval}; 409 "already resolved by <who>"; Stop cancels: met. `Allow answers the approval...`, `Deny answers with the reject option`, `a 409 says it was already resolved, and by whom`, `Stop cancels the run`, `Stop is not offered when nothing runs`.
4. Outbox with idempotency keys survives offline and reload: met. `a prompt written offline waits, survives a reload, and is sent once when back` (Playwright `setOffline`; stored queue has no session token), `a send whose answer was lost is retried with the same key and happens once`, `every POST carries an Idempotency-Key`.

## Notes
- Removing a pending chip uses `POST .../cancel` (member), not `DELETE .../pending/{task_id}`: the hub's policy requires `admin` for the DELETE (`auth/policy.rs`) and web sessions are capped at `member`, so DELETE returned 403. The spec (client-api 5.3, 5.5) says to use DELETE; `cancel` on a queued task removes it from the queue too (`threads/core.rs`).
- `api.js` `request()` cannot send `Idempotency-Key`, so `outbox.js` has `keyedRequest()` (token in header only); on 401 it calls `request()` once so the shared unauthorized handler runs.
- Attachments are uploaded when picked, so picking while offline fails with a message; only the prompt (text and uploaded file parts) is queued offline.
- Pre-existing, not fixed: the `Stop cancels the run` test took 46 s in the first run (1.5 s in the second hub); likely hub warm-up.
