# M2-010 report: thread titles, rename, archive/delete, D1 FTS5 search, deep links

## Summary

- `GET /v1/threads` lists the caller's org's threads from the D1 task index (`tasks`), filtered by `machine_id`, `status`, `agent`, `workspace`, with `q` as FTS5 over titles, `archived=true` to include archived threads, and keyset pagination by `updated_at`.
- Titles: the first prompt's first line (v1 heuristic ported, 80 characters, word boundary) unless the client set one at create or with `PATCH`. `PATCH /v1/threads/{id}` (member, audited) sets `title` and `archived`; `DELETE /v1/threads/{id}` (admin, audited, `Idempotency-Key`) soft-deletes.
- The Thread DO upserts the thread's index row after requests and events that change the title, status or lifecycle. The sync is one hook call in `do/thread.rs`, which is outside the item's listed paths (see Files changed).
- Deep links: `GET /t/{id}` is a 302 to `/#/t/{id}`. `/.well-known/apple-app-site-association` and `/.well-known/assetlinks.json` are built from `[vars]` and return 404 while those vars are empty.
- Migration `0008_tasks_index.sql` adds `machine_id`, `agent`, `workspace_path`, `last_seq`, `deleted_at` to `tasks` and one index. The 0002 status CHECK is kept; the client names map onto it.

## Known limitations and decisions

- Threads that existed before this deploy have no index row, so they are not listed until their next index-changing event. There is no backfill (discovered work).
- A failed D1 upsert is logged, not retried, so the index can be stale until the next change to that thread.
- `last_seq` and `updated_at` in the index are refreshed only at index-changing events, not on every streamed event. This keeps D1 writes off the streaming path.
- The `done` status has no producer yet. The stored CHECK allows `done`, `failed`, `cancelled`; `done` maps to `done` in the list, but nothing writes it.
- A deleted thread still answers `GET /v1/threads/{id}` and still accepts prompts, since the item asks for a soft delete of the list entry only.
- `DELETE` needs an `Idempotency-Key` (client-api.md §3). The Worker writes the audit row before the Thread DO checks the key, as the existing pending-task delete does.
