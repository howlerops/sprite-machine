# WEB-004: PWA + Web Push

## Summary
- The page is an installable PWA: manifest, three PNG icons (192, 512, maskable 512), and `sw.js`, which caches the app shell (network first, cache when offline) and never touches `/v1/*`.
- `web/src/push.js` registers the worker, subscribes (VAPID key from the hub) and registers the subscription; a "Enable notifications" button is added to the session list bar (the subscription renews silently once permission is granted). Sign out unsubscribes and removes the token the worker holds.
- The worker shows pushes (ids only; generic title; the thread title is fetched with the session token kept in IndexedDB `sm-push`, in a header only). A click opens `/t/<id>`; Allow/Deny post the payload's own `option_id` with an `Idempotency-Key`, and fall back to opening the thread if the answer fails.
- `run_worker_first` now excludes `/sw.js`, `/manifest.webmanifest`, `/icons/*`; `helpers-hub.sh` gives the test hub a per-run VAPID key.

## Acceptance criteria
1. Installable PWA (manifest, icons, shell-caching worker): met. `the manifest is linked, valid and its icons are PNGs`, `a service worker is registered at / and caches the app shell, never the API`, `the shell opens offline from the cache`.
2. VAPID subscription registered with the hub; click opens /t/<id>; Allow/Deny answer the Interrupt: met. `with permission the page subscribes with the hub key and registers it; a push reaches the service worker` (subscribe gets the hub's key; the hub then pushes to the registered endpoint), `a notification click opens /t/<id>`, `Allow answers the interrupt with its own option id and an Idempotency-Key` (request inspected: option `allow`, key present, token in header only), `Deny answers with the reject option`, `an answer that cannot be made opens the thread instead` (409 fallback).
3. pwa.spec.js asserts manifest, worker registration, and a push through the hub's fake provider received by the worker: met. The push test decrypts the hub's body (RFC 8291) at a fake push service and delivers it with CDP `ServiceWorker.deliverPushMessage`; it asserts ids-only payload, the shown notification and its actions. `without a stored session the worker still shows a generic notification`.

## Notes
- Chromium has no push service in the sandbox, so `PushManager.subscribe` is stubbed in the test (endpoint = the fake service, test-owned keys). The hub-to-service leg (encryption, VAPID, queue) is real. Real-device subscribe is not covered.
- The spec (client-api 5.8) says `GET /v1/push/vapid-public-key` returns `{ "key" }`; the hub returns `{ "public_key" }`. The page accepts both; the hub was not changed.
- The notification click and actions are exercised with a synthetic `NotificationEvent` in the worker (Playwright cannot click OS notifications); `waitUntil` is wrapped in try/catch because script-made events refuse it.
- Test uses `PW_EXPERIMENTAL_SERVICE_WORKER_NETWORK_EVENTS=1` (set in the spec) to see the worker's own requests.
- Permission prompt (`requestPermission` from the button tap) is not tested: the tests grant it up front, so the page subscribes automatically.
