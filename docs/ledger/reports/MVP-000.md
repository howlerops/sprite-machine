# MVP-000 report: tracer bullet

## Summary

`cargo run -p cli -- e2e tracer` runs the whole loop. It builds the hub with `worker-build`, starts `wrangler dev --local` on a free port in its own process group, and wires acp-mock → sidecar bridge → runner tunnel client in-process. A headless client prompts, answers the approval through the hub, and sees `RunFinished{success}`. The run ends with exit 0 and kills the wrangler process group.
`protocol::turn_event` now has serde types for the envelope and all 27 variants, plus `ThreadSeq`. All 32 examples round-trip to an identical `serde_json::Value`.
Every component except the harness and `protocol::turn_event` is a marked TRACER STUB. `protocol::tunnel` was used as is, with no changes.

## Acceptance criteria

1. **Met.** `cli e2e tracer`:
   - runs `worker-build --release` in `crates/hub` (with `RUSTFLAGS`/`RUSTC_WRAPPER` unset and `CARGO_PROFILE_RELEASE_STRIP=false`);
   - starts `wrangler dev --local --ip 127.0.0.1 --port <free> --persist-to <tmp>` in a new process group (`process_group(0)`, which has the same effect as `setsid` for group kill);
   - runs acp-mock in-process over `tokio::io::duplex`, with one prompt, one `request_permission` (`expect: "allow"`) and `end_turn`;
   - stops wrangler on every exit path. The `Wrangler` guard's `stop()`/`Drop` sends `kill -TERM -- -pgid`, waits up to 5 s, then sends `kill -KILL` and reaps the process. The guard covers success, an error return and a panic unwind, and a Ctrl-C/SIGTERM handler drops the guard. The output and the SIGINT test above show this.
2. **Met.** The client sees UserMessage, RunStarted{prompt}, TextMessage*, ToolCallStart, Interrupt{approval} and RunFinished{interrupt}. It then POSTs the allow answer to the hub, and the hub appends `InterruptResolved` and queues `command{approval}`. The runner receives the approval as a tunnel `command` frame, emits `RunStarted{resume, parent_run_id}` and answers ACP. acp-mock checks that the answer is an allow (otherwise the prompt fails and the client would see `RunError`). The run ends with ToolCallEnd, TextMessage*, RunFinished{success} and exit 0. `check_sequence` in `crates/cli/src/e2e/tracer.rs` asserts the exact rule 6 shape and that `parent_run_id` names the paused run. A second answer from another key gets HTTP 409.
3. **Met.** `protocol::turn_event` types are covered by these tests:
   - `every_example_round_trips_to_an_identical_value` (all 32 files);
   - `every_variant_has_a_schema_and_an_example` (`Event::TYPE_NAMES` == `events/*.schema.json`, and every variant appears in an example);
   - `thread_seq_stamps_gap_free_from_one`;
   - `unknown_event_type_is_ignored_not_an_error`, `other_envelope_versions_are_rejected`, `null_task_and_run_ids_are_serialized` and `ids_follow_the_spec_pattern`.

   `protocol::tunnel` needed no change.
4. **Met.** See the stub table below. Each stub file's first line is `// TRACER STUB: replaced by <item>`. "No auth" is stated in the `worker.rs` stub header and docs, and in the `state.rs` and `runner/src/tracer.rs` headers.
5. **Met.** The hub stamps `seq` with `ThreadSeq` (`hub::tracer::thread::ThreadState::append` refuses `seq ≠ 0`), and producers send `seq: 0`. The `sidecar` test `tracer_bridge` asserts this, and `HubState` nacks an already-stamped envelope. The client (`client_core::tracer::Applied::apply`) asserts `seq == last + 1` and drops duplicates. The cli asserts the same again over the whole list.

## Spec issues found

1. **Who emits `UserMessage` is not stated.** turn-event.md §4.1 says "From ACP `session/prompt` input". tunnel.md's `prompt` command carries `message_id`, `parts` and `author`, but it does not say whether the hub or the runner appends `UserMessage`. The tracer has the runner emit it, before `RunStarted{prompt}`. M2-008 and M1A-006b need one answer.
2. **Thread creation for a `prompt` is undefined in the MVP subset.** `prompt` targets "an existing thread", and `thread_open`/`dispatch` are outside the MVP frame set. The tracer creates the thread on its first `POST /threads/{id}/prompts`, hosted by the `machine_id` in that body.
3. **The client HTTP API is not specified.** That covers the prompt and interrupt-answer paths, the bodies, `Idempotency-Key`, and the 409 body `{error, resolved_by}`. The tracer uses the shapes suggested in the task. A short spec would stop M2-008 and M3-001 from diverging.
4. **The status for open tool calls at a successful end is unstated.** turn-event.md §5 rule 5 requires every tool call to be closed before the final terminal event, but gives a status only for `RunError` (`failed`). The tracer bridge closes leftovers as `failed` on success too. The tracer script closes its tool call itself, so this path is not exercised.
5. **One auto-response pair per DO.** `setWebSocketAutoResponse` holds one pair per object. A DO that hosts both tunnel and subscription sockets can auto-answer only `{"t":"ping"}`, so the subscription `{"type":"ping"}` is answered in `websocket_message`. The real design has separate Thread and Machine DOs, so each kind gets its own pair. This is a note for M2-008 only.
6. **Schema validation of Rust output is not done.** turn-event.md §8 asks that "JSON from Rust must validate against these schemas (`jsonschema` crate in dev-dependencies)". The tracer proves this only for the examples: they round-trip to identical values, and `validate.py` validates those values. Rust-built envelopes are not validated against the schemas (proposed below for M1A-006a).
7. **The workspace profile applies to the hub, not the crate profile.** `worker-build` in the workspace uses the root `[profile.release]`, so the spike's `opt-level = "z"`, `lto = true` and `strip = false` do not apply. The tracer passes `CARGO_PROFILE_RELEASE_STRIP=false` by env (the root `Cargo.toml` is outside my allowed files). The wasm is 1,493,110 bytes against the spike's 487,908 (no lto, opt-level 3).
