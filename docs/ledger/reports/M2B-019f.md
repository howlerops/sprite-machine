# M2B-019f: hub: a pre-/rc task counts as busy

## Summary
- `thread_open` has a new optional field `running_task` (tunnel.md §3.4): the task the runner is already running when it registers the thread.
- The Thread DO's `init_thread` records that task as `Running` (a placeholder with `has_run: true`), so a prompt that arrives before the runner's earlier events waits in the pending queue. The runner's `UserMessage` fills the record in; its `RunFinished{success}` / `RunError` ends it as for any task.
- The TUI session names the task from its log at `/rc` (`Upstream::open_running`, default method, so `cli`'s Upstream is unchanged); the tunnel upstream queues the extended frame.

## Spec text added (docs/specs/tunnel.md §3.4, after the example)
> `running_task` (optional): the `task_id` of a task the runner is **already running** when it registers the thread, one it started itself before `/rc` (the TUI's offline turns). The Thread DO counts that task as running from the moment the thread exists, so a prompt that arrives before the runner's earlier events do waits in the pending queue (§3.5) instead of starting and being sent down to an agent that is busy. The runner's `UserMessage` for the task fills in the record and its `RunFinished{success}` / `RunError` ends it, as for any task; the hub sends no `prompt` command for it. A `running_task` that is not a valid id is `nack{invalid_envelope}`. Omit it when the agent is idle.

## Acceptance
"Register with /rc while an offline-started task runs; a phone prompt waits for it and runs once; test (native + live)": MET.
- Why it was broken: `thread_open` carried nothing about a running task, and the offline `UserMessage`/`RunStarted` follow as separate `event` frames. A phone prompt between the two saw an idle thread, started, and went down to a bridge that refused it. (When the events had already landed the hub was already busy; the new native test pins that too.)
- Native, hub: `threads::tests::a_task_the_runner_started_before_it_registered_is_busy_for_the_first_shared_prompt` (phone and terminal prompts wait, nothing goes down, the phone's runs once when the offline task ends, then the terminal's), `a_registration_without_a_running_task_leaves_the_thread_idle_and_a_bad_task_id_is_refused`, `a_cancel_of_the_offline_task_goes_down_as_a_cancel_command`; `machines::tests::thread_open_passes_the_task_the_runner_is_already_running_to_the_thread`; protocol `thread_open_with_a_running_task_roundtrips`.
- Native, runner: `session::registering_during_an_offline_task_names_it_and_the_phone_prompt_runs_once_after` (real bridge + acp-mock: `/rc` mid-task names the task; after it ends the hub's prompt runs once, no "refused"), `session::registering_an_idle_session_names_no_task`.
- Live: `machine_do::a_task_started_before_the_thread_was_opened_makes_the_first_phone_prompt_wait` (phone prompt right after `thread_open` is `pending`; no command down while the offline task runs; one `prompt` command after it ends; `UserMessage`s `tk_off`, `tk_ph1`). Without the field the prompt would be `started` and sent down at once.

## Notes
- `TunnelSink::thread_open` (runner/src/tunnel/io.rs) is outside this item's paths, so `TunnelUpstream::open_running` in `tui/host.rs` queues the extended `thread_open` itself through `shared.enqueue` under the same `local_threads` guard. See discovered work.
- `cli/src/e2e/rc.rs` implements `Upstream` without `open_running`; it falls back to the plain `open` (its session is idle at registration, so nothing is lost).
