# M2B-005: `sm login` device-code pairing + trusted device + keychain

## Summary

- Hub: RFC 8628 device pairing under `/v1/devices/*` (code, token, approve, deny, list, revoke, policy). Only the SHA-256 of the device code is stored; the credential is minted at the single successful poll and the pairing is claimed (`approved` -> `consumed`) first, so it is handed out once.
- A paired machine is a normal `machines` row plus Machine DO provisioning, exactly like `POST /v1/machines` (new column `machines.origin = 'device'`); revoke reuses `machines::admin::revoke_machine` (tunnel closes with `auth_revoked`).
- Runner: `sm login --hub <url>` prints user code, verification URL and a unicode QR, polls with the server interval (honours `slow_down`), stores the credential in the OS keychain (`keyring`, linux keyutils / apple native, no openssl) with a 0600 file fallback (forced by `SM_CREDENTIAL_FILE`). `KeychainCredentials` implements the tunnel `CredentialSource` (read per connect, wipe on revoke).
- Trusted-devices modelling: see criterion 1 below. Enforcement at the tunnel is NOT wired (needs a file outside my scope); proposed as a ledger item.

## Acceptance criteria

1. Hub: MET.
   - code / token / approve / deny: live `code_start_has_the_rfc_8628_fields`, `pending_then_approved_gives_one_credential_and_the_registry_reuses_machines` (pending, 401 without session, 403 viewer, 404 unknown code, approve by member, grant, second poll `invalid_grant`), `polling_faster_than_the_interval_is_slow_down` (interval 5 -> 10), `a_denied_pairing_is_access_denied_and_never_a_machine`, `an_unknown_device_code_is_invalid_grant`. The owner session comes from `POST /v1/auth/bootstrap`.
   - expired_token (10 min) cannot be reached on a live hub: native `devices::tests::expired_after_ten_minutes_even_if_approved` (injected clock); slow_down arithmetic and single use also native (`polling_too_fast_is_slow_down_and_the_interval_grows`, `full_flow_...`). Provisioning failure leaves no row and the pairing is retryable: `a_failing_machine_do_leaves_no_row_and_the_pairing_can_be_retried`.
   - list / revoke reuse the registry: live test lists the device, appears in `GET /v1/machines`, `DELETE /v1/devices/{id}` (member 403, owner 200) closes the live tunnel with `close{auth_revoked}` and `revoked_at` is set; admin-API machines are 404 on the device route.
   - Rate limit on `POST /v1/devices/code`: stubbed with a TODO in `service::start` (allowed by the item).
   - `require_trusted_devices` (existing column `orgs.require_trusted_devices`, migration 0002; no new column): `PUT /v1/devices/policy` (admin, audited) sets it, `GET /v1/devices` reports it. Model: `machines.origin` is `device` (approved pairing = trusted) or `admin` (admin-API; stays allowed). `devices::trust::tunnel_allowed` / `machine_may_connect` implement "with the setting on, only a machine with a known vouched origin and not revoked may connect". Live test `the_trusted_devices_setting_is_admin_only_and_keeps_admin_machines_allowed` (setting on: admin machine still opens a tunnel, a new pairing still completes); native `trust::tests::rule` and `list_revoke_and_policy_...`. CAVEAT: the tunnel route / Machine DO do not call `machine_may_connect` yet (`machines/routes.rs` and the DO are outside this item's files). Since every machine today has a vouched origin, nothing is refused today; the gate is ready for a future non-vouched creation path. See discovered work.
2. Runner: MET. `full_flow_pending_then_approved` (prints user code, URL, unicode QR; device code in JSON body only; credential never printed), `slow_down_backs_off_by_the_servers_interval_or_five_seconds` (sleeps 5,5,10,15), `expired_code_ends_the_login_and_stores_nothing`, `a_hub_that_never_expires_the_code_is_given_up_on`, `denied_pairing_ends_the_login_and_stores_nothing`, `the_file_fallback_is_0600_and_used_when_the_keychain_fails` (file 0600, dir 0700), `a_working_keychain_holds_the_secret_and_no_file_is_written`, `keychain_credentials_read_on_each_connect_and_wipe_on_revoke`, `wipe_clears_a_keychain_credential_too`, `sm_login_runs_end_to_end_with_the_forced_credential_file` (real `sm` binary, `SM_CREDENTIAL_FILE`), `plain_http_is_for_loopback_hubs_only`.
   - Not tested: the real OS keychain (headless CI has none). The keychain is exercised through the `Keychain` trait with in-memory fakes; `OsKeychain` (keyring) compiles and is used by `CredentialStore::from_env`, falling back to the file on any error.

## Notes

- Linux keychain is keyutils (kernel session keyring: lost at reboot / not shared across sessions); then `load` falls back to the file only if one was written. A persistent store on Linux would need secret-service (libdbus). Flagged below.
- `sm login` does not take a machine name: the approver names the device at approve time.
- Plain `http://` hubs are refused for non-loopback hosts so the credential never crosses the network in clear.
