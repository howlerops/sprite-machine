# M2-011a report: push follow-ups

## Summary

- `scripts/hub-test.sh` generates a P-256 VAPID key per run (node, in memory) and passes `VAPID_PRIVATE_KEY` and `VAPID_PUBLIC_KEY` as `--var`. The DEV_FIXTURES derivation from `ATTACHMENT_SIGNING_KEY` (`Vapid::dev_derived`, its fallback in `env::load_vapid`) is removed.
- A job whose send partly fails is re-queued with `subscriptions` = the pending subscription ids only (`NotifyJob::follow_up`, delayed 5 s, at most `MAX_ATTEMPTS` = 5 sends). Delivered subscriptions are never sent to again. The original message is acked, not retried.
- `process_job` now reads everything (targets, prefs) before the first send, so a database error never happens after a partial send.
- Live: `a_partly_failed_job_is_retried_for_its_failed_subscription_only` (one 503, one 201; the 201 gets one push). Against the stale wasm (old whole-message retry) this test saw 4 pushes instead of 3, so it fails without the change.

## Files changed

- `scripts/hub-test.sh`: per-run VAPID key (node `generateKeyPairSync`), `--var VAPID_PRIVATE_KEY` and `--var VAPID_PUBLIC_KEY`.
- `crates/hub/src/notify/env.rs`: `load_vapid` reads only the `VAPID_PRIVATE_KEY` secret; no fallback.
- `crates/hub/src/notify/webpush.rs`: `Vapid::dev_derived` removed.
- `crates/hub/src/notify/job.rs`: `NotifyJob` gains `subscriptions: Option<Vec<String>>` and `attempt: u32` (both serde-default); `MAX_ATTEMPTS`; `NotifyJob::follow_up`.
- `crates/hub/src/notify/service.rs`: `process_job` reads first, sends second; `JobReport.retry: bool` replaced by `JobReport.pending: Vec<String>`; a `410` whose deletion fails stays pending (a send to a gone endpoint reaches nobody).
- `crates/hub/src/queues/notify.rs`: the consumer re-queues `follow_up` with `MessageBuilder::delay_seconds(5)` and acks the original; a failed re-queue is `retry()`d; a DB error before any send is `retry()`d as before.
- `crates/hub/src/notify/tests.rs`: `a_partly_failed_job_is_followed_up_for_its_failed_subscriptions_only`; updated fields and the `pending` assertions.
- `crates/hub/tests/notify.rs`: `PushService::answer_for` (per-endpoint script), `count_for`; new live test `a_partly_failed_job_is_retried_for_its_failed_subscription_only`; header comment on the key.
- `crates/hub/src/notify/mod.rs`: flow doc.

## Acceptance criteria

1. Met. `scripts/hub-test.sh` generates the P-256 key per run and passes `VAPID_PRIVATE_KEY`/`VAPID_PUBLIC_KEY` as `--var`. The live tests use it: `an_interrupt_leads_to_one_encrypted_vapid_signed_push_with_ids_only` verifies the VAPID JWT against the served `k` (the derived public key). `Vapid::dev_derived` and the fallback are gone (grep finds no `dev_derived`). No key material in source or config: the key lives only in shell variables and the wrangler arguments. The one exception is the `VAPID_PUBLIC_KEY` placeholder in `crates/hub/wrangler.toml` (see Discovered work).
2. Met. `a_partly_failed_job_is_retried_for_its_failed_subscription_only` (live): one endpoint answers 503, the other 201. The 201 endpoint gets exactly one request; the 503 endpoint gets two, both with `Topic` = the task id and the same payload. Native: `a_partly_failed_job_is_followed_up_for_its_failed_subscriptions_only` (the follow-up carries only the pending id, `attempt` is capped at `MAX_ATTEMPTS`). `gone_subscriptions_are_deleted_and_temporary_failures_ask_for_a_retry` was updated to the `pending` report.
