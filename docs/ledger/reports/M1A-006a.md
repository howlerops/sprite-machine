# M1A-006a report: protocol::mapping ACP→TurnEvent + golden tests

## Summary

- `protocol::mapping::acp_turn::AcpTurnMapper` is a pure, IO-free, clock-free per-thread state machine that maps ACP v1 (`session/update`, `session/new`, `session/request_permission`, `elicitation/create` form and url, the prompt response, cancel) to TurnEvent envelopes with `seq: 0`. Timestamps are passed in and ids come from an injected `IdSource`.
- It covers every §4 row that has an ACP source: text and reasoning, tool calls (upsert by id, args, results, diff and terminal `Activity`), plan, session, usage and thread state (snapshot before delta), approval, form and auth interrupts with the pause and resume (new `run_id`), cancel, expiry, error and every stop reason. Every ACP-derived envelope keeps the ACP payload in `raw`.
- `validate_sequence` / `validate_complete` / `SequenceValidator` (in `acp_turn/validate.rs`) implement §3 `seq` and §5 rules 1 to 8 plus the §4 scopes.
- 37 golden cases (`tests/golden/acp_turn/<case>/{input.json,expected.json}`), each checked against the JSON schemas, `validate_complete`, a serde round trip and raw preservation, plus 32 `validate_sequence` tests (29 negative, 3 positive) and 10 behaviour tests: 79 tests in `golden_acp_turn`.

## Design notes

- `on_session_update_json(&Value)` is the faithful entry point: `raw.payload` is the `update` as sent, and an update this build cannot parse (a newer `sessionUpdate`) becomes a `Raw` event. `on_session_update(&SessionNotification)` re-serializes the typed value (key order and omitted defaults such as `status: "pending"` can differ from the wire).
- While a run is paused on an interrupt, every ACP input (updates, further permission requests, the prompt response, tee'd terminal calls) is queued and replayed by `resume()` after the resume `RunStarted`. A queued request pauses the run again and the rest stays queued (`request_permission_two_pauses`).
- The hub emits `InterruptResolved` and the first `UserMessage`; the mapper only offers `on_interrupt_resolved` (cancel, expiry, golden logs) and `note_interrupt_resolved` (bookkeeping when the hub resolved it).
- `ToolCallStart` is emitted only for a new call or changed title, kind, status or locations (only the changed fields); `ToolCallArgs` and `ToolCallResult` only when the value changed, so ACP's resend of the whole `content` collection does not re-emit diffs or results.
- Diffs larger than 96 KiB (JSON-escaped), text deltas larger than 96 KiB and terminal output larger than 64 KiB per call are split; ACP terminal output kept for the closing snapshot is capped at its last 128 KiB.

## Spec issues (most literal reading implemented)

1. turn-event.md §4 names `crates/protocol/src/mapping/acp.rs`; the ledger item places the module at `mapping/acp_turn*`.
2. `user_message_chunk` has no run-scoped TurnEvent (`UserMessage` must precede `RunStarted` and the hub owns it). It maps to `Raw{acp}` inside a run and is dropped outside a task. A `session/load` replay would need a `replay_user_message` entry point.
3. §5 rules 1, 3 and 6 do not say which run carries the `RunError` of a task cancelled or expired while paused (no run is open). Implemented as `InterruptResolved{cancelled|expired}` for each open interrupt, a `RunStarted{resume}` run, closing `ToolCallEnd{failed}`, then `RunError`. Updates queued during the pause are dropped.
4. §5 rule 6 is enforced strictly: `RunFinished{success}` and `RunError` need every raised interrupt resolved; `RunFinished{interrupt}` must list every open one.
5. §5 rule 5 says tool calls are closed before the task's final terminal event but only prescribes `ToolCallEnd{failed}` on `RunError`. For `RunFinished{success}` with a call still open the mapper emits `completed` for `end_turn` and `failed` for `max_tokens`, `max_turn_requests`, `refusal`.
6. `ToolCallResult.content` is `ContentPart[]` (text or https file). Images, audio, binary resources and non-https links produce no part (the verbatim `raw` keeps them). Embedded text resources become text parts.
7. `session_info_update` becomes `StateSnapshot{thread}` `{title, pending_tasks: []}` then `StateDelta`. The `thread` scope is hub-owned (`pending_tasks`), so the runner's snapshot would clobber the hub's queue if forwarded as is. Not forwarding runner `thread` state, or merging it in the hub, needs a decision in M1A-006b / hub items. `updatedAt` alone is ignored.
8. A different ACP `messageId` on consecutive chunks starts a new message (ACP semantics); §4.2 only talks about chunk kinds.
9. Permission options whose `optionId` is not a valid Id are dropped (the schema pattern would reject them); the tool call id is hashed instead (§2).
10. §4.4 says the closing terminal snapshot repeats all output; it is capped at the last 128 KiB so it fits §2.
11. The `session/prompt` response `raw` is synthesized as `{"stopReason": …}` (the mapper is given the stop reason, not the whole response).
12. Commit attribution: the task text asks for `Co-Authored-By: Claude Opus 5.5`; the session guidance names `Claude Sonnet 5.5` and a `Claude-Session` line. The commit follows the session guidance (the actual model).
