# M3-006 report: attachments (picker, paste, drag-drop) and inline images

## Summary
- `compose/attach.rs` (window-free): the limits and checks that refuse a file before anything is uploaded (`check`: 1 byte to 20 MB like the hub, programs refused by extension or MIME type), `read_file` (size and type checked from metadata, so a huge file is never read), `AttachmentSet` (items with name, size, MIME type and a state Pending / Uploading / Uploaded(part) / Failed; `gate()` answers Empty / Ready(parts) / Waiting / Blocked), the injectable `Uploader` trait, `NoUploader` (signed out) and `HttpUploader` (`POST {api}/attachments` with `Idempotency-Key`, then `PUT` the bytes to the signed `upload_url`, answers the `{type:"file"}` part with name, MIME type, size and sha256), `keyed_by_parts` (another set of files is another idempotency key).
- `compose/attach_bar.rs`: `AttachBar`, the strip both composers embed: "Attach files" button over an injectable `FileChooser` (`SystemChooser` = the platform dialog), `paste` (images and copied files; plain text is left to the field), chips with name, size, state (progress %), Retry on a failed upload and Remove, dismissible rejection lines, a "blocked" notice and an "uploading" note. `DropZone` tracks an external file drag over a composer and delivers the files on release.
- `compose/thread.rs`, `compose/mod.rs` (hook-up only): both composers hold an `AttachBar`, wire paste on the text field and the drop zone on the root. Send uploads first. A failed upload blocks the send until Retry or Remove. Thread composer: with attachments the send is `ComposerEvent::Intent(Intent::Prompt{parts: [text?, file...]})`, which the shell already enqueues unchanged, so no shell change was needed; without attachments it is still `ComposerEvent::Send`. New-task composer: the file parts are appended to `prompt.parts` of the `POST /v1/threads` body. `ThreadComposer::set_upload_target` / the new-task `Target` choose the hub the uploads go to.
- `task/media.rs` + `task/transcript.rs` + `task/mod.rs`: image parts (bitmap `file` parts with an http(s) URL) become `RowKind::Image` rows after a tool call's text rows. The pane draws a thumbnail (taller row, `Row::height`), a click opens a full-size panel with a Close button, and an image that cannot load (fetch error, HTTP error, bytes that are not an image by magic number, decode failure) shows a note instead. Bytes are fetched by an injectable `ImageFetcher` (`HttpFetcher` = GET with timeout and the 20 MB cap) into a `MediaCache`, one fetch per URL.
- `locales/en/compose.ftl`: `compose-attach-*` and `compose-media-*` strings (the media strings live here because only this file may change).
- `tests/attachments.rs`: 22 tests; 4 unit tests in `attach.rs` and `media.rs`.

## Criteria
- Picker with an injectable chooser, chips with name/size/remove: MET. `the_picker_adds_chips_with_name_and_size_and_remove_drops_them` (fake `FileChooser`; chip labels "notes.md, 1.5 KB, ready to upload"; Remove drops the chip).
- Paste of a clipboard image: MET. `pasting_an_image_attaches_it_and_text_still_pastes_as_text` goes through the real path (clipboard, focus in the field, `ctrl-v`) and gets `pasted-image-1.png`, `image/png`; a text clipboard is not taken.
- Drag-drop onto the composer: MET for both composers (`dropping_files_on_the_thread_composer_attaches_them`; the new-task test drops after the user typed). That second case failed with `on_drop` and with `capture_any_mouse_up`, see Notes.
- Over-limit or refused type rejected with a Fluent message before upload: MET. `files_over_the_limit_or_of_a_refused_type_are_rejected_with_a_message` (a 21 MB sparse file and a `.exe` give "huge.bin is 20.0 MB, over the 20.0 MB limit, so it was not attached." / "setup.exe (...) is a type that cannot be attached."; the good file stays; the uploader was never called). Native: `the_hubs_size_limit_and_refused_types_are_enforced_before_upload`, `files_are_checked_from_their_metadata_before_they_are_read`.
- Upload first, progress/failed states, failed upload blocks send with a retry: MET. `send_uploads_first_then_the_prompt_carries_text_and_file_parts` (nothing emitted until both uploads finish), `a_failed_upload_blocks_send_until_it_is_retried` (status "upload failed: could not reach the hub (connection reset)", Retry button, "blocked" notice, a second Send stays blocked and does not repeat the good upload, Retry uploads only the failed file, then Send goes through with text and both files). Progress is shown as "uploading N%" (the fake sets 40; `HttpUploader` sets 20 after the create call and 100 when stored; there is no byte-level progress).
- Prompt carries the parts per spec: MET. Thread composer: `Intent::Prompt` parts `[text, file, file]`. New task, against a fake hub that speaks §5.6: `the_new_task_uploads_attachments_to_the_hub_then_creates_the_thread_with_their_parts` checks the POST (bearer token, `Idempotency-Key`, `{name, mime_type, size}`), the PUT (bytes, `Content-Type`, no bearer token sent to the signed URL) and that `/v1/threads` gets `[{type:text}, {type:file, name, mime_type, url, size, sha256}]`. `the_http_uploader_creates_puts_and_answers_the_file_part` and `hub_refusals_become_upload_errors_with_a_reason` (413 => over the limit, 403, storage 500, hub down) cover the uploader alone.
- Image parts render inline (thumbnail, click for full size) with a fallback: PARTLY MET. Tested: `an_image_part_renders_inline_and_a_click_opens_it_full_size`, `an_image_that_cannot_load_shows_a_fallback_note_instead`, `image_parts_become_taller_image_rows_after_the_tool_text`, `the_cache_loads_sniffs_and_reports_failures`, `the_http_fetcher_gets_bytes_and_reports_a_missing_image`. But image parts are only drawn where they reach the transcript as content parts, today a tool call's `content`. A user message's own image parts are not drawn: `client-core`'s `UserView` keeps only the joined text (`[file: name]`) and drops the URL, and `client-core` is outside this item's paths. `media::push_image_rows` is ready for it, see Discovered work (first entry).
- Fluent strings with a catalog test: MET. `every_attachment_and_media_string_id_is_in_the_catalog` (every `compose-attach-*` / `compose-media-*` id used in `attach.rs`, `attach_bar.rs`, `media.rs`, `transcript.rs` exists and formats with its arguments, and every id in the section is used).

## Notes
- gpui at this pin does not count a file drag as mouse input, so after the user types, the last input is "keyboard" and `Hitbox::is_hovered` is false for the whole drag. `on_drop` and `capture_any_mouse_up` (both hover-gated) then silently drop the files. `DropZone` avoids this: `on_drag_move::<ExternalPaths>` (not hover-gated) records the files while the pointer is inside the composer, and a raw `window.on_mouse_event` listener installed from a `canvas` delivers them on release.
- `window.find(id)` panics for an absent element (as noted in M3-005); absence is checked with `find_all(id).is_empty()`.
- Notifications raised inside `update_window` are not drawn by a `render_frame` in the same closure; the test helpers pump in `cx.update`, then render in a separate `update_window`.
- Attachments upload when Send is pressed, not when added, so a removed file never reaches the hub. A retry of a failed create keeps its idempotency key per attachment; a new-task retry with a different set of files gets a different thread key (`keyed_by_parts`) so the hub never sees one key with two bodies.
- A new task still requires prompt text (`Invalid::NoPrompt`, in `new.rs`, which this item may not change); the thread composer accepts an attachment-only message.
- Signed attachment URLs live 24 hours (hub `URL_TTL_MS`). A prompt held in the outbox while offline for longer would carry expired URLs.
