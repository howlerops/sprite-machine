# M2-009 report: hub attachments in R2 + signed URLs (attempt 1)

## Summary

- `POST /v1/attachments` (member, `Idempotency-Key`, audited) answers 201 `{upload_url, url, expires_at, part}`. `part` is the FilePart `{type:"file", url, name, mime_type, size}`.
- Both URLs are HMAC-SHA256 signed over op, org, attachment, expiry, and (PUT) size and MIME type. Verification is constant-time and checks expiry; a bad or expired URL gets 403.
- PUT stores bytes in R2 (`BLOBS`) under `orgs/{org}/attachments/blob/{id}`. Above 20 MB gets 413; a size other than declared gets 400. GET returns the bytes with the declared Content-Type.
- R2 is behind a `Blobs` trait with a `MemoryBlobs` fake. Native unit tests (24) and live tests (6) cover the criteria.
- Decision needing leader confirmation: the live test cannot receive `ATTACHMENT_SIGNING_KEY` from `scripts/hub-test.sh` (see Spec issues 1).

## Acceptance criteria

1. POST 201 with URLs; PUT stores in R2 under an org-scoped key; >20 MB gets 413; size mismatch gets 400; GET returns the bytes with the declared type. MET.
   - Live: `create_upload_and_fetch_round_trip_the_bytes_with_the_declared_type`, `an_upload_of_the_wrong_size_or_over_twenty_megabytes_is_refused`.
   - Native: `a_body_of_another_size_than_declared_is_refused_and_not_stored`, `a_body_over_twenty_megabytes_is_refused_with_413_and_not_stored`, `upload_then_fetch_returns_the_bytes_with_the_declared_type`.
2. HMAC-SHA256 signed, constant-time, expiry checked; tampered, expired and cross-object URLs get 403; FilePart in response. MET.
   - Native: `a_tampered_signature_is_refused`, `any_changed_claim_breaks_the_signature`, `an_expired_signature_is_refused_from_the_expiry_instant`, `a_signature_from_another_key_is_refused`, `tampered_or_expired_urls_are_forbidden`, `a_url_from_one_org_does_not_reach_another_orgs_object`, `a_url_does_not_reach_another_attachment`.
   - Live: `tampered_and_cross_object_urls_are_forbidden`, `an_upload_url_cannot_read_and_a_content_url_cannot_write`.
3. R2 behind a trait with an in-memory fake; native unit tests for signing, size limits, key scoping; live tests run by `hub-test.sh attachments`. MET.
   - Fake: `MemoryBlobs` in `store.rs`. Signing, size limits and key scoping: the native tests above.
   - Also native: `create_needs_a_valid_idempotency_key`, `the_same_key_replays_...`, `the_same_key_with_another_body_is_422`, `a_key_is_forgotten_after_the_idempotency_window`, `a_viewer_cannot_create_and_nothing_is_written`.

Not covered: the viewer 403 is native only (no live viewer session exists under DEV_FIXTURES).

## Spec issues and decisions

1. `scripts/hub-test.sh` starts wrangler with only `--var BOOTSTRAP_OWNER_TOKEN`, so `[env.dev.vars]` does not apply and the live Worker has no signing key. The item's file list does not allow editing the script or `crates/hub/.dev.vars`. I added a fallback: when `DEV_FIXTURES=1` and no `ATTACHMENT_SIGNING_KEY` is set, `routes.rs` uses a placeholder `DEV_SIGNING_KEY` (same value as `wrangler.toml`). Without DEV_FIXTURES and without a key, the route fails closed with 500. Leader: confirm, or move the var into `crates/hub/.dev.vars` or the script (`--var ATTACHMENT_SIGNING_KEY:...`) and drop the fallback.
2. Idempotency is stored in R2 (`orgs/{org}/attachments/idempotency/{sha256(user, key)}`), not D1. No migration was allowed. Two concurrent same-key requests can both create (last record wins). The 24-hour window is enforced by `created_ms`; R2 has no TTL.
3. The 413 status for oversize declarations and bodies uses error code `invalid_request`. §4 does not list 413.
4. The create response adds `part` next to `upload_url`, `url` and `expires_at`. Acceptance 2 asks for the FilePart in the response.
5. Both URLs expire after 24 hours (`URL_TTL_MS`), so the runner can fetch them at dispatch time.
6. Attachments that are created but never uploaded are not cleaned up (no R2 lifecycle rule is configured).
7. The signed URL origin comes from the request URI (`scheme://authority`, scheme defaults to https). Production is https; local dev is http.
