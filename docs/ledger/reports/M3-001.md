# M3-001 report: client-core: TurnEvent subscription client, view models, cache, outbound queue

## Summary

## Spec issues

1. **§6 "events with seq ≤ last applied only rebuild in-progress state"**: ambiguous. I drop replayed events at or below the applied seq and do not re-apply them. In-progress state lives in memory across reconnects; after a cold start it is rebuilt from the cached log (`ThreadSync::restore`), not from the replay. The literal "rebuild" reading would double-apply text deltas and tool-call appends.
2. **§6 snapshot `at_seq`**: the snapshot is only installed when `at_seq == applied`. An older one is ignored and a newer one is a protocol error. Both follow from `R-1 ≤ after`, which the spec implies but does not state.
3. **client-api §3/§5.3 vs MVP-000 tracer hub**: the production contract says clients never send an `Actor`, but the tracer hub's routes require `machine_id`, `author` and `resolved_by` in the body. I send them only when set (`Intent` fields are `Option`), and the tracer sets them. Needs a leader decision on whether the tracer hub is updated or the contract is changed.
4. **Base URL / `/v1` prefix**: client-api §5 puts every route under `/v1`, but the MVP-000 hub serves `/threads/...` with no prefix. The client takes the base URL including any prefix; it does not add `/v1` itself.
5. **Cached unknown events**: an `Event::Unknown` serialises as `{"type":"Unknown"}`, so the cache loses the original type name. Harmless for the view (it is ignored either way), but a future client that understands the type would not see it after a restart.
6. **Auth**: `Subscription` and `HttpTransport` accept an optional bearer token. No token source exists yet (M2-003a).
