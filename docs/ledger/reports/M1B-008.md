# M1B-008 report: benchmark scripts per gates.yaml

## Summary

- `spikes/bench/run-desktop.sh` implements the Linux desktop benchmark for gpui-kit end to end: a
  real mode (release builds, `agui-fixture --scenario transcript-10k --rate 200`, five runs under
  `xvfb-run` on lavapipe, `/proc/<pid>/status` VmHWM sampling, marker-based cold start, `xdotool`
  input for key-to-glyph) and a `--dry-run` that prints every step and runs nothing. The real mode is
  not run here (the release build needs more disk than is free).
- The spike does not emit the required instrumentation yet (no bench marker, no frame log, no
  fixture connection). The contract is in the header of `run-desktop.sh` and in the proposed items
  below. Until those land, real mode fails at the marker wait (it reports this clearly and does not write results).
- `spikes/bench/results.schema.json` (JSON Schema 2020-12) defines one evidence file per gate, per
  candidate, per device. `spikes/bench/validate_results.py` checks the schema and the rules a schema cannot
  express: percentiles recomputed from samples, `value` per statistic, `pass == value <= threshold`,
  thresholds copied from `gates.yaml`, path agreement, and pinned versions per candidate.
- `summarize_desktop.py` turns the raw run logs into the five desktop evidence files and validates them.
  It was smoke-tested on synthetic logs in the scratchpad (not committed): all five files validate and
  the validator rejects corrupted variants (wrong pass, wrong p95, wrong value, unknown gate, path mismatch, empty samples).
- `spikes/bench/HARD_GATES.md` gives a numbered procedure, pass/fail rule and evidence for each of the 12
  hard gates. `spikes/bench/mobile/README.md` gives the measurement procedure for the numeric gates on iPhone
  and Android (Instruments / `xctrace`, `adb` / `dumpsys` / `am start -W` / bundletool / Perfetto).
- `gates.yaml` is unchanged. No threshold was edited.

## Design decisions to review

- **Gated value.** Frame time and key-to-glyph: samples are the pooled raw values; the gated value is the median over the five runs of each run's own p95 (per gates.yaml: "median of 5 runs; p95 is computed within each run"). Cold start and RSS: one sample per run; the gated value is the median. Binary size: one sample. The schema records this in `statistic`, so a reader can tell which rule produced `value`.
- **Frame time.** Interval between consecutive frame presentations after the first interactive frame. Keys are injected through XTEST, so key-to-glyph starts at the app's KeyDown receipt and excludes X-server dispatch. Both are noted in the script header.
- **Units.** Decimal MB (10^6 bytes) for RSS and binary size. The gates say MB and do not say MiB.
- **Cold start.** The origin is the wrapper's pre-exec timestamp; the end is the spike's marker. The spike has no inbox yet, so the marker is the transcript shell's first interactive frame. The result notes say so.
- **gpui pin.** The root `Cargo.toml` pins gpui by crates.io version (`gpui-pre =0.3.10`), not by git rev, so `pinned.gpui_rev` holds `gpui-pre@0.3.10`. gpui-component is pinned by git rev, which the script reads from the root `Cargo.toml`.
- **Pins per candidate.** The validator requires the pins that gates.yaml `rules.version_pin` names for gpui-kit (gpui_rev, gpui_component_rev), flutter (flutter, flutter_rust_bridge) and hybrid (all four). The `example` candidate has no requirement.
- **Workload constants.** `runs`, `events_per_second`, `transcript_events` and `diff_lines` are read from `gates.yaml` at run time, not copied into the script.

## Known gaps

- `xdotool` is not installed in this container, and `scripts/setup-dev.sh` does not install it. Real mode checks for it and fails clearly. Proposed item M1B-008d.
- The spike does not render the common workload (5k-line diff, terminal output, approval card) and does not connect to the fixture. Proposed items M1B-008a and M1B-008b.
- The results directory for real runs (`results/gpui-kit/desktop_linux/`) is written only by real mode, so no real evidence exists yet. Proposed item M1B-008c.
- `HARD_GATES.md` and `mobile/README.md` are procedures only; they have not been exercised on a device (that is M1B-010).
