# M2B-004a: tunnel durability

## Summary

Down commands are now committed (`last_down_seq` + idempotency key, one transaction) only when the bridge reports them processed, so a crash between receive and apply gets the command redelivered. `Store::restart_outbound_stream` is one transaction and the client lock is gone; `Store::outbound_since` and `Store::seen_key` were added. A late `processed` from before a fresh stream is matched by idempotency key, so it cannot ack or commit a new command with the same seq. `Sender::set_max_inflight` makes the client honour `welcome.max_inflight`.

## Acceptance criteria

1. **Met.** `a_command_received_but_not_processed_is_redelivered_after_a_crash` (runner): first client drops with the command unprocessed (`last_down_seq` 0, key unseen), a new client on the same Store sends `hello.last_down_seq=0`, the hub redelivers, the bridge gets it once, ack follows `processed`; a later renumbered-stream replay of the key is acked but not applied. Also `commands_reach_the_bridge_in_order_and_are_acked_after_processing`, `a_repeated_idempotency_key_is_acked_but_not_applied_twice`.
2. **Met.** `restart_outbound_stream_never_loses_a_concurrent_enqueue` (sidecar, 300 concurrent enqueues vs repeated restarts); the runner's `outbox_lock` is removed; `outbound_since_returns_only_the_tail_in_order`, `seen_key_reads_without_recording`. The pump now reads only the tail via `outbound_since`.
3. **Met.** `a_late_processed_from_before_a_fresh_stream_cannot_ack_a_new_command`: old command seq 1, fresh stream reuses seq 1 with another key, late `processed(1)` sends no ack and leaves `last_down_seq` 0 (it only records the old key); the real `processed` for the new command acks.
4. **Met.** `welcome_max_inflight_caps_unacked_up_frames` (client, window 2, 5 events) and protocol unit test `welcome_max_inflight_caps_the_unacked_frames_in_flight`.

## Design notes and limits

- `TunnelCommands::processed(seq)` maps the seq to the idempotency key from its FIFO of delivered commands (bridge reports in order) and sends the key to the client. A command the bridge never reports would shift the mapping; the bridge trait is outside this item.
- Exactly-once holds across a crash only up to the bridge's own effect: if the runner dies after the bridge applied a command but before the commit, it is applied again on redelivery (at-least-once with key dedupe after the commit).
- Keys fed to the bridge and not yet processed (`in_flight`) are kept across reconnects, so redelivery after a reconnect in the same process is not fed twice.
