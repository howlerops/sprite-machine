# M1B-002 report: agui-fixture scenarios

## Summary
- `crates/agui-fixture` serves four canned threads over the subscription protocol of `docs/specs/turn-event.md` §6: `transcript-10k`, `diff-5k`, `terminal`, `approval`. Each scenario is a deterministic script built from `protocol::turn_event` types. The server stamps `seq` with `ThreadSeq`, replays the log for `?after=n` (run-boundary catch-up), and answers `POST /threads/{id}/interrupts/{iid}` with first-answer-wins, Idempotency-Key replay and 409 `already_resolved` carrying `resolved_by`.
- The test target `crates/agui-fixture/tests/scenarios.rs` has 7 tests. All pass. They cover schema validation of every emitted event, a §5 ordering checker, the 10k WebSocket stream, the 5k diff, the terminal, approval resume with 409, and mid-run reconnect.
- The §5 checker lives in the test file over wire JSON. It is independent of the fixture's own code (see the discovered work below).

## Acceptance criteria
1. **met**. WebSocket scenarios run end to end. `transcript-10k` streams at least 10,000 events, and the received log equals the scripted log. `diff-5k` reassembles to exactly 5,000 lines in chunks of at most 96 KiB. `terminal` streams 1 KiB append chunks and closes with `exit_code` 0. `approval` pauses at `RunFinished{interrupt}` and resumes after the answer. Every emitted event validates against `crates/protocol/schemas/turn-event`, and every shipped example validates too.
2. **met**. Seq is gap-free from 1 to N on every connection. A mid-run reconnect with `?after=K` replays from the run boundary R (the open run's `RunStarted`). The test checks that the second connection's first seq is R, that the union of both connections covers 1..=N, and that the only duplicates are R..=K. A second answer to an interrupt returns 409 `already_resolved` with `resolved_by` set to the first resolver. A repeat with the same Idempotency-Key returns 200.

## Spec issues
- **SPEC-001-terminal.** `turn-event.md` §4.4 says a terminal "ends with a snapshot carrying `exit`", but `snapshot` replaces stored content. The spec does not say whether that closing snapshot must repeat the streamed output or whether it should be a patch or an empty snapshot. The fixture repeats the full output in the closing snapshot, so both readings give the same stored result. The spec should state this explicitly.
- **§5 checker location.** `protocol::turn_event` has no `validate_sequence()` yet (M1A-006a). The checker therefore lives in `tests/scenarios.rs` and should move to `protocol` once it lands.
