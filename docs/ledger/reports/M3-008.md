# M3-008: desktop task view (transcript, reasoning, tool calls, terminal activity)

## Summary
- `TranscriptPane` (`crates/client-gpui/src/task/transcript.rs`) is a `v_virtual_list` of fixed-height text rows built from `client-core` `ThreadView` -> `TaskView` -> `Transcript` items; `tools.rs` builds the rows for tool calls, diff/plan/terminal/policy activities, interrupts and checkpoints.
- Thread header rows come from `ThreadView` state: title, mode, context tokens, machine presence; each task ends with its status row.
- 26 of the 32 TurnEvent examples render. The other 6 (StepStarted, StepFinished, SubagentStarted, SubagentFinished, SubagentError, Raw) cannot: client-core view models drop them. See `blocked_on` below.
- Layout of the visible window of the 10k fixture: p95 about 1 ms per frame (debug build); real frame time is not measurable here.

## Criteria
**"Every TurnEvent variant rendered from client-core view models": PARTLY MET (26 of 32 examples; 6 blocked on client-core).**
- `every_turn_event_example_has_an_expectation`: fails if an example file has no table entry (or an entry names a missing file).
- `every_turn_event_example_renders_from_the_view_models`: for each example, feeds it (plus the minimal prerequisite examples) through `ThreadView::apply` and asserts the rendered rows contain specific text; standalone examples must add text that is absent without them.
- `all_example_variants_are_laid_out_in_the_window`: one thread of all renderable examples; every row appears as a laid-out row in the headless window.
- `known_gaps_are_still_gaps`: the six unrendered examples must leave the view unchanged; it fails as soon as client-core keeps them, so the list cannot go stale. This documents the gap; it is not a rendering.
- Support tests: `untrusted_text_is_shown_as_text` (control chars stripped, markup stays literal), `long_bodies_are_capped_with_a_more_row`, `every_task_string_id_exists_in_the_catalog_and_is_used`.
- blocked_on: `Transcript::apply` ignores `StepStarted/Finished`, `SubagentStarted/Finished/Error` and `Raw`, and `ThreadView` has no step or subagent state. client-core would need to expose these (for example `Item::Step`, `Item::Subagent` with name/status/child ids) before the pane can render them. I did not change client-core.

**"Virtualized; the 10k fixture stays within the gates.yaml desktop thresholds": MET for what is measurable headlessly.**
- Test: `ten_thousand_events_are_virtualized_and_within_budget` (agui-fixture `Transcript10k`, 10,026 events -> 11,585 rows, 226 KB of row text).
- At most 60 rows are laid out (about 27 fit in the 600 px window) at the top and after each of 40 scroll steps; rows far down and the first row after scrolling are not laid out; row count <= 8 per event; row text < 16 MB.
- Layout time per frame while scrolling: median 0.7 ms, p95 1.0 ms in a debug build (budget 100 ms in debug, 16.7 ms in release, the gates.yaml `frame_time_p95`). Building all rows takes about 25 ms; `set_thread` about 24 ms.
- `the_pane_follows_a_growing_transcript` covers follow-tail scrolling.
- NOT measured: real frame time (paint and GPU, per ADR 0001a), rss_peak against 300 MB, cold start, the 200 events/s streaming workload, binary size. The time budget covers layout only, on this machine, in a debug build.

## Limits
- Rows are wrapped by character count (110 columns), not measured pixels; long lines are truncated visually at the pane edge.
- Tool input/output, reasoning, diffs and terminals are capped (12/12/30/20 lines) with a "N more lines" row; no expand control yet.
- Diff rows are a minimal prefix/suffix diff; the real diff view is a separate item. Approval buttons and time left belong to the approval item; the transcript shows the interrupt, its options and its resolution as text.
- The whole thread's row list is rebuilt on each `set_thread` (about 25 ms at 10k events); fine for now, incremental updates are a possible optimization.
- Cost and context percentage are not computed; only the raw context tokens are shown.
