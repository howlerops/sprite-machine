# M3-008b: desktop task view: incremental row updates

## Summary
- `TranscriptPane::set_thread` no longer rebuilds every row. A new `RowCache` (`task/row_cache.rs`) keeps the flat row list plus, per segment (header, each transcript item, each task's status line), the item the rows were built from, the approval card used, and how many rows the segment owns. `sync` walks the thread, compares each item with the one its rows came from (`PartialEq`), and rebuilds and splices only the segments that differ.
- The pane no longer clones the whole `ThreadView` on each update (it used to keep `thread.clone()`). The cache keeps a clone only of an item that changed; the open diff reads its activity from the cache.
- `toggle_expanded` and `set_approvals` call `RowCache::refresh`, which rebuilds only the items whose expansion or card changed.
- Diff summary counts come from `DiffStats` (tools.rs): `(added, removed)` per activity id, keyed by a hash of the diff's path and texts, so a `DiffModel` is built once per diff content.
- Old entry points are unchanged: `thread_rows`, `thread_rows_expanded`, `thread_rows_with_cards`, `item_rows`, `item_rows_with_cards`, `task_rows`, `activity_rows`, `set_thread`, `rows()`. They remain the full-rebuild reference; a test requires the incremental rows to equal them.
- Rows that depend on the item number (the "more lines" / "show less" expand key) are rebuilt only when the item has a capped body and its number or expanded state changed.

## Criteria with evidence
- **Applying one event updates only the affected rows:** `one_appended_text_delta_rebuilds_one_items_rows`: 200 messages, sync builds 200 items; one delta to `m77` gives `items_visited 200, items_rebuilt 1, rows_rebuilt 1`; a new message gives 1 and 1; an unchanged thread gives 0 and 0. After each step `cache.rows()` equals `thread_rows_with_cards`.
- **Expansion rebuilds one item:** `expanding_an_item_rebuilds_that_item_alone`: 40 items, expand item 11 via `refresh` gives `items_rebuilt 1` and rows equal the full rebuild with that key; a later `sync` keeps it and rebuilds 0; collapsing rebuilds 1.
- **Diff counts computed once per content:** `diff_summary_counts_are_computed_once_per_diff_content`: first sync `diff_builds 1`; ten later syncs with other items streaming `0`; expand and collapse the diff (item rebuilt) `0`; new content for the same activity `1` and the row text changes from `+100 -1` to `+2 -1`.
- **10k fixture streaming at 200 ev/s within the frame budget:** the streaming test above asserts p95 per-frame row-update time <= the existing budget (`FRAME_BUDGET_DEBUG`/`RELEASE`), `items_rebuilt <= events in the batch` for every frame, diff models built <= number of diffs, and every 400th frame (and the last) rows == full rebuild. Numbers above.
- **Existing transcript tests green:** all 17 pass unchanged.
- **Each new test fails without the change:** they use `RowCache`, `last_update` and `UpdateStats`, so they do not compile without it. I also mutation-checked: forcing "item changed" in `sync` failed the text-delta, expansion and streaming tests; disabling the `DiffStats` lookup failed the diff-count test. Both mutations were reverted.

## Limits
- `sync` still visits every item and compares it with its cached clone (O(items) per update, memcmp-like cost); this is where the 2 ms median at 10k events goes. A per-item version from client-core would remove it.
- A growing message or terminal item is rewrapped whole when it changes (cost proportional to that item).
- `RowCache::activity` is a linear scan, used only while a diff is open.
- Release-build timing and real frame time (paint) are not measured.
- The shell still calls `set_thread(&ThreadView)` per snapshot; I did not touch shell/**.
