## Spec text added (docs/specs/tunnel.md §3.6b, abridged)
> A prompt typed on the runner itself (the `sm` TUI) in a **shared** session is not sent to the agent by the runner. It goes up, the Thread DO queues it exactly like a phone's prompt, and it comes back down as a `prompt` command (§3.5) when its turn in the queue comes. The hub alone orders local and phone prompts; the runner needs no timing window and never races a phone prompt for the bridge.
>
> `prompt_submit` (up, sequenced) `{thread_id, task_id, message_id, parts}`. `task_id` and `message_id` are chosen by the runner, so the `prompt` command that comes back can be matched to the line typed.
>
> The Machine DO checks the thread is hosted by this machine (else `nack{forbidden}`) and passes it to the Thread DO, which handles it **exactly as it handles `POST /v1/threads/{id}/prompts`**: if no task runs it starts the task, otherwise it adds it to the pending queue behind the prompts queued before it. The author is the machine's local user (as in §3.6a). The idempotency key is the `task_id`, so a retransmit queues one task, never two.
>
> A prompt the Thread DO refuses is `nack{invalid_envelope}`. The runner does **not** write the line's `UserMessage` to its own log or hand it to the bridge; the `prompt` command is the only way it reaches the agent while the session is shared.
>
> **Offline TUI.** A session that is not registered with a hub keeps sending its lines straight to the bridge, one at a time, as before.

## Limits
- A line the hub nacks (for example an empty prompt) is dropped; the runner only logs the nack. A shared line typed while an offline-started task still runs on the bridge can be refused by the bridge (the hub thinks the thread is idle); the same exposure exists for phone prompts today.
