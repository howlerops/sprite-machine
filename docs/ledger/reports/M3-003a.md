# M3-003a: onboarding notices a machine within seconds

## Summary
- The shell's machines timer now ticks every `machines::ONBOARDING_REFRESH_EVERY` (3 s). It fetches on every tick while `onboarding_visible` and otherwise only every `TICKS_PER_REFRESH` (10) ticks, i.e. the old `REFRESH_EVERY` (30 s) cadence. `refresh_machines` still no-ops while a fetch is in flight, so refreshes do not stack.
- `onboarding_visible` treats an inbox whose fetch failed (error set, no rows) as empty, so a failing `GET /v1/threads` with no machines shows the steps instead of the inbox error.

- `crates/client-gpui/tests/onboarding.rs` (hub gets threads_status, machines_hits, machines_delay_ms; 4 new tests)

## Criteria
- Short cadence while visible, 30 s after: `the_refresh_returns_to_the_slow_cadence_once_onboarding_is_gone` (3 short ticks give 3 fetches; after completion 3 short ticks give none, one REFRESH_EVERY gives one).
- Machine detected within the short interval: `a_machine_appearing_is_noticed_within_the_short_onboarding_interval` (advance_clock by 3 s only).
- Failing inbox fetch, empty machines: `a_failing_inbox_fetch_with_no_machines_still_shows_the_steps`.
- No stacking: `a_slow_machines_answer_is_not_stacked_by_the_short_interval` (8 short ticks while the first answer is delayed, exactly 1 request).
- Fail-without-change: with the two view.rs edits reverted, the cadence, short-interval and inbox-failure tests fail (the stacking test passes by design, it guards the existing guard).
